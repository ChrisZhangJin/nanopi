# nanopi v0.12 — WASM plugins as event subscribers

> Design note, not a spec-in-waiting. Decides one thing: how a WASM
> extension observes nanopi's lifecycle events, which today only shell
> hooks can see. Read §1 for the problem, §4 for what actually gets
> built, §5 for the parts that will bite.

---

## 1. The problem is not "nanopi has no events"

nanopi emits eleven lifecycle events, all wired into the agent loop
already (`src/agent/hook.rs`, fired from `src/agent/loop_.rs`):

`pre_tool_use` · `post_tool_use` · `user_prompt_submit` ·
`session_start` · `session_end` · `before_agent_start` · `turn_start` ·
`turn_end` · `message_end` · `session_before_compact` ·
`session_compact`

The defect is that **nanopi has two extension systems that cannot see
each other**:

| | add tools | add commands | see events | veto / transform | hold state | cost per fire |
|---|---|---|---|---|---|---|
| shell hooks | ✗ | ✗ | ✓ (11) | ✓ | ✗ — fresh process | fork + exec |
| WASM plugins | ✓ | ✓ | ✗ | ✗ | ✓ — `Store` persists | one function call |
| PI `ExtensionAPI` | ✓ | ✓ | ✓ (~28) | ✓ | ✓ | in-process |

In PI these are one object. In nanopi, an author who wants "add a tool
**and** watch every prompt" must ship a `.wasm` *and* a shell script,
with no way to share state between them. That split is what v0.12
closes.

It closes it in one direction only. Shell hooks keep their veto; WASM
plugins get to watch. See §3 for why that asymmetry is deliberate
rather than a first-cut compromise.

## 2. What nanopi's events are, in PI's terms

nanopi's eleven are a *subset of PI's with different names*, so "match
PI" is not a well-defined target. The mapping:

| PI event | nanopi |
|---|---|
| `session_start` | same |
| `session_before_compact` | same |
| `session_compact` | same |
| `before_agent_start` | same |
| `turn_start` | same |
| `turn_end` | same |
| `message_end` | same |
| `tool_execution_start` | `pre_tool_use` |
| `tool_execution_end` | `post_tool_use` |
| `input` | `user_prompt_submit` |
| `session_shutdown` | `session_end` |

### 2.1 Naming: PI's names, on BOTH surfaces

**Decision: one vocabulary. The Claude Code names are dropped.**

| old (Claude Code) | new (PI) | where it appears |
|---|---|---|
| `pre_tool_use` | `tool_execution_start` | `[[hooks.*]]` key, `HookEvent`, `NANOPI_EVENT` |
| `post_tool_use` | `tool_execution_end` | same |
| `user_prompt_submit` | `input` | same |
| `session_end` | `session_shutdown` | same — see §2.2 |

This is a **breaking change to `config.toml` / `settings.toml`**, taken
deliberately in v0.12 rather than carried forever. Existing hook
configs must be renamed by hand; nanopi should say so rather than
silently ignoring an unknown key (§7).

An earlier draft of this note argued for keeping Claude Code's names on
the shell surface and PI's on the WASM surface, on the grounds that the
two have different audiences. That was rejected, and the reason is
worth recording: **two vocabularies for eleven events is a permanent
tax on every future reader**, paid so that a config file written for a
different tool keeps working. One name per event, chosen to match the
project nanopi is a port of.

The trade being accepted, stated plainly so nobody rediscovers it:

- The README's "Claude Code hooks" framing is now only half true. The
  *protocol* is still Claude Code's — JSON on stdin, exit code 2 to
  refuse, `tool_name` / `tool_input` / `hookSpecificOutput` payload
  fields — but the event *names* are PI's. Both READMEs need that
  sentence changed, not deleted.
- A user arriving from Claude Code writes `[[hooks.pre_tool_use]]` and
  gets nothing. Hence the unknown-key error in §7: this is the one
  case where a config typo must be loud.

PI has no shell hooks — but it is worth recording that it *used to*,
because the question comes back. `migrations.ts:228` still warns
`hooks/ directory found. Hooks have been renamed to extensions.`, next
to the same warning for `tools/`. PI had a `~/.pi/agent/hooks/`
directory and a separate custom-tools directory, and folded both into
one extension mechanism; the session schema's v2→v3 bump renaming
`hookMessage` to `custom` is the same cleanup. Every remaining `hook`
in PI's source is an in-process callback (`agent-session.ts:461`,
`emitToolResult`), not a subprocess. Searching the whole PI repo for
`PreToolUse` / `pre_tool_use` / `UserPromptSubmit` returns nothing.

So those three names are absent from PI not because PI never
considered the shape, but because PI concluded a separate hook layer
should not exist. That makes borrowing PI's vocabulary for nanopi's
shell layer worse, not better: `tool_execution_start` was coined for an
in-process TypeScript callback, not for "fork a process, feed it JSON
on stdin, exit 2 to refuse" — a protocol nanopi copied verbatim from
Claude Code, down to the `tool_name` / `tool_input` /
`hookSpecificOutput` payload fields and the exit-code-2 semantics.

Why nanopi keeps the shell layer that PI dropped is §8.

### 2.2 `session_end` → `session_shutdown`, and it gains a `reason`

Today `session_end` fires exactly once, from two places — TUI teardown
(`mode/tui.rs`) and after the turn in `-p` (`mode/print.rs`) — and
carries no reason. PI's `session_shutdown` carries
`reason: "quit" | "reload" | "new" | "resume" | "fork"`, and fires
whenever the session is torn down, not only when the process exits.

Matching the name without matching that is worse than not matching it:
a PI author would reasonably expect `/new` to fire it. So both change
together.

New emit points, all four already rebuild the Agent and therefore
already end a session:

| site | `reason` |
|---|---|
| TUI teardown / `-p` completion | `quit` |
| `KeyAction::NewSession` (`/new`) | `new` |
| `KeyAction::OpenResumePicker` → resume (`/resume`) | `resume` |
| `execute_fork` (`/fork`) | `fork` |
| `KeyAction::ApplyImport` (`/import`) | `import` |

Two deliberate divergences from PI's list:

- **No `reload`.** nanopi's `/reload` updates the live Agent in place
  (`refresh_live_agent`) rather than rebuilding it, so no session ends.
  Emitting `session_shutdown` there would be a lie.
- **`import` added.** PI has no `/import`; nanopi does, and it swaps the
  Agent exactly like `/resume`.

`reason` goes in the payload's `arguments` object, i.e.
`{"reason":"new"}`.

**Correction to an earlier draft of this note**, which claimed that is
"where the compaction events already put theirs". It is not.
`run_session_hooks` hardcodes `arguments: json!({})`
(`src/agent/hook.rs:423`) and the compaction events smuggle their
reason through the `subject` parameter, which lands in the payload's
`session_id` field. So this needs a new `arguments: Value` parameter on
`run_session_hooks` and an update to all four of its callers — a real
signature change, not a fill-in-the-blank.

**The `matcher` subject does not change** — it stays the session id, as
documented in `run_session_hooks`. Matching on the reason instead would
be more useful than matching on a UUID, but that is a second breaking
change to a second field and it is not on the table for v0.12; noted
here so the option isn't lost.

Three decisions taken during plan review, all of them "cheap now,
a separate round later":

**(a) `session_start` gains the same `reason`.** PI's carries
`startup | reload | new | resume | fork`; nanopi's becomes
`startup | new | resume | fork | import` — same two divergences as
`session_shutdown` (no `reload`, plus `import`).

Without this, `/new` fires a `session_shutdown` that says *why* and
then a `session_start` that does not: two halves of one switch, one
of them informative. A hook author has to correlate by timing. The
change is the same `arguments` parameter and the same emit sites, so
it rides along rather than costing a second pass.

**(b) The compaction events' reason moves into `arguments.reason`.**
Today `session_before_compact` / `session_compact` pass `threshold`
or `manual` through `subject`, which lands in the payload's
**`session_id`** field. That field name is a lie: a hook reading
`session_id` gets `"threshold"`. Since `run_session_hooks` is gaining
an `arguments` parameter anyway (above), all four session-lifecycle
events should carry `reason` in the same place, rather than two
following the new convention and two keeping a special case.

The `matcher` subject for the compaction events stays the reason —
that part is genuinely useful and documented.

**Sharpened after plan review.** `run_session_hooks` sets
`session_id: Some(subject)` unconditionally, so simply *adding*
`arguments.reason` would leave `session_id` still equal to
`"threshold"` for compaction events: the lying field would remain,
now with a correct value sitting next to it. Half-fixing it means a
*second* breaking payload change later to finish the job.

So `run_session_hooks` takes the matcher subject and the session id as
**separate parameters**. After this, for every session-lifecycle event:

| field | value |
|---|---|
| payload `session_id` | the real session id, always |
| payload `arguments.reason` | the reason, always |
| env `NANOPI_SESSION_ID` | the real session id, always |
| `matcher` subject | session id for start/shutdown, reason for the two compaction events (unchanged) |

The env var is the third surface with the same bug and was found during
plan review: `hook.rs:429` sets `NANOPI_SESSION_ID` from `subject` too,
so a `session_compact` hook currently reads
`NANOPI_SESSION_ID=threshold`. A payload-only fix would have left it,
and finishing it later would have been yet another breaking change.

That is a third breaking payload change — a hook currently reading
`session_id` to get `threshold`/`manual` must read `arguments.reason`
instead. Taken now because it is one more parameter on a function
already being changed, and because shipping the lie one release longer
buys nothing.

**(c) The fire-before-swap ordering gets a testable seam.** The four
new emit points sit at agent-swap sites in `src/mode/tui.rs`, which
cannot be unit-tested without a terminal. Grep-plus-compile proves the
call *exists*; it cannot prove the call happens **before** the old
Agent is replaced — and that ordering is the only real defect this
task can introduce. One line late and the hook fires against the new
session.

So extract the ordering into a small helper — "fire
`session_shutdown` with this reason on the outgoing Agent, then
install the new one" — and test that. Not a refactor of the four
sites' surrounding logic; just enough of a seam that the sequence is
asserted somewhere. Scope creep, accepted deliberately, because the
alternative is a bug only human review can catch.

### 2.3 No compatibility period

Decided: the four retired keys stop working outright. No
`serde(alias …)`, no dual-key parsing, no warn-and-accept path, no
migration shim. There are effectively no users of these keys yet, so a
compatibility layer would cost more than it buys.

That makes two things load-bearing rather than cosmetic:

- **The unknown-key error is the only thing between an old config and
  silent breakage.** It must be a hard config-load error, not a stderr
  line that scrolls past, and it must recognise the four retired names
  specifically rather than falling into a generic "unknown key" path:

  ```
  unknown hook event "pre_tool_use" — renamed to "tool_execution_start"
  in v0.12 (see docs/v0.12-events.md §2.1)
  ```

- **`.release-notes-v0.12.0.md` is a deliverable of Stage A**, not a
  follow-up. It is how the break is communicated, so its Compatibility
  section leads with the rename table, the `session_shutdown`
  semantics change, and the two payload changes from §2.2(b).
  (v0.11.0's release notes say "No breaking changes"; v0.12's cannot.)

  **And it inherits v0.11.0's.** v0.11.0 is sealed but will not be
  released — it ships as part of v0.12.0. So everything in
  `.release-notes-v0.11.0.md` reaches users for the first time under
  the v0.12.0 tag: WASM extensions, the gated host functions, plugin
  slash commands, the Pi lifecycle hooks, mid-stream steering,
  configurable tool exec mode. So do the six fixes in `ead885a`
  (`/tools`, the parallel tool-card header, `url_allowlist`
  wildcards, the blockquote/thinking collision, the musl libunwind
  noise, the `-p` thinking/reply run-on).

  Writing v0.12.0's notes as if they cover only the event work would
  ship the entire extension feature set unannounced. They must absorb
  v0.11.0's content rather than link to a tag that does not exist.

(An earlier draft said `session_start`'s missing `reason` was out of
scope. Decision (a) in §2.2 supersedes that — `session_start` gains
`reason` in v0.12.)

The two therefore differ by design, and the host translates at the emit
site:

```
  emit site (one internal HookEvent)
      ├── shell hooks     → "pre_tool_use"          (Claude Code)
      └── handle-event    → "tool_execution_start"  (PI)
```

One table, four rows, in `hook.rs`. The cost of the split is that table
plus this paragraph; the cost of *not* splitting is that one of the two
audiences reads foreign names forever.

Corollary for the implementation: `list-events` and the config's
`events` list both use **PI names**, so a plugin author never types a
Claude Code name. Rejecting a Claude Code name in `events` with "did you
mean `tool_execution_start`?" is worth the four lines.

Twenty PI events have no nanopi counterpart:

```
project_trust          resources_discover     session_info_changed
session_before_switch  session_before_fork    session_before_tree
session_tree           context                before_provider_request
before_provider_headers after_provider_response agent_start
agent_end              agent_settled          message_start
message_update         tool_execution_update  model_select
thinking_level_select  user_bash
```

**Out of scope for v0.12.** Each needs a new emit site, which is
separate work from the delivery mechanism this note designs. Three are
worth their weight later — `before_provider_request` (retry and payload
shaping), `context` (per-turn context injection), and
`session_before_fork`. Two must be permanently refused for plugins:
`message_update` and `tool_execution_update` fire per streaming delta,
which would mean hundreds of boundary crossings per turn (§5.2).

## 3. Decision: observe-only

`handle-event`'s return value is **ignored**. A plugin cannot block a
tool call, rewrite arguments, or alter a prompt.

This is not timidity, it is what makes the locking model sound.
`ComponentBridge` serializes guest entry behind a `Mutex`, and tools
execute in parallel by default. If events could veto, every delivery
would have to *wait* for that lock — so plugin A's 30-second tool call
would stall the turn that plugin A's event handler was asked about
(§5.3). Observe-only lets the host use `try_lock` and simply drop the
delivery when the plugin is busy: a slow plugin can then never extend a
turn, and there is no lock cycle to reason about.

The veto capability is not lost to users. Shell hooks already have it,
already run at the same emit points, and already have a documented
protocol for it.

If a future version wants veto from WASM, the cost is a second
component instance dedicated to the event channel, so that guest event
code never contends with guest tool code. That is the upgrade path;
it is not v0.12.

## 4. The mechanism

### 4.0 How a plugin ends up receiving an event

Two phases: a subscription negotiated once at load, then delivery on
every emit.

**Phase 1 — load time. The plugin asks; the config grants; the host
keeps the intersection.**

```
   config.toml                          watcher.wasm
 ┌───────────────────────────┐      ┌──────────────────────────────┐
 │ [[extensions]]            │      │ export list-events() -> [    │
 │ path = "watcher.wasm"     │      │   "tool_execution_start",    │
 │ allow_network = false     │      │   "input",                   │
 │ events = [                │      │   "turn_start"               │
 │   "tool_execution_start"  │      │ ]                            │
 │ ]                         │      │                              │
 └─────────────┬─────────────┘      └──────────────┬───────────────┘
               │ GRANTED by the user               │ REQUESTED by the plugin
               │                                   │
               └──────────────┐     ┌──────────────┘
                              ▼     ▼
                      ┌───────────────────┐
                      │    ∩  intersect   │   ← neither side alone is enough
                      └─────────┬─────────┘
                                │
            ┌───────────────────┴────────────────────┐
            ▼                                        ▼
   DELIVERED                              REQUESTED, NOT GRANTED
   tool_execution_start                   input, turn_start
            │                                        │
            ▼                                        ▼
   ┌──────────────────────┐          warn at load:
   │ subscriber table     │          "watcher: requested `input`,
   │ event → [plugin,…]   │           `turn_start` — not in `events`,
   │ (precomputed, so an  │            not delivered"
   │  event with no subs  │
   │  costs a slice check)│          (a plugin that looks broken
   └──────────────────────┘           should say why)
```

**Phase 2 — every turn. One payload, two kinds of subscriber.**

```
 run_turn
    │
    ├── emit before_agent_start ───────────────┐
    ├── emit input ────────────────────────────┤
    │                                          │
    ▼ loop {                                   │
    ├── emit turn_start ───────────────────────┤
    │                                          │
    ├── for each tool call (parallel):         │
    │     ├── emit tool_execution_start ───────┤
    │     ├── tool.execute()  ← takes the      │
    │     │                     bridge lock    │
    │     └── emit tool_execution_end ─────────┤
    │                                          │
    ├── emit turn_end ─────────────────────────┤
    │   }                                      │
    └── emit message_end ──────────────────────┤
                                               │
                                               ▼
                            ┌──────────────────────────────────┐
                            │ EMIT                             │
                            │ payload JSON built ONCE, shared  │
                            │ by every subscriber below        │
                            └────┬────────────────────────┬────┘
                                 │                        │
                ┌────────────────▼─────┐   ┌──────────────▼──────────────┐
                │ shell hooks          │   │ WASM subscribers            │
                │ fork + exec, JSON    │   │ (subscriber table, §4.0-1)  │
                │ on stdin             │   │                             │
                │                      │   │ try_lock()  ← NEVER waits   │
                │ name: pre_tool_use   │   │  ├─ Ok  → handle-event(     │
                │       (Claude Code)  │   │  │      "tool_execution_    │
                │                      │   │  │       start", payload)   │
                │ CAN veto:            │   │  │      2s epoch budget     │
                │  Block / Transform   │   │  │      return IGNORED      │
                └──────────┬───────────┘   │  └─ Err → drop + debug log  │
                           │               │         (plugin is busy)    │
                           │               └──────────────┬──────────────┘
                           ▼                              ▼
                 turn continues, or the           turn is NEVER affected
                 tool call is refused             (observe-only, §3)
```

**Why `try_lock` rather than a blocking lock.** `ComponentBridge`
serializes guest entry, and tools run in parallel, so the case below is
ordinary rather than exotic:

```
 t=0s   plugin A's `query` tool starts ──── bridge A LOCKED ─────┐
 t=0s   plugin B's `fetch` tool starts                           │
 t=0s   emit tool_execution_start (for B's call)                 │  A is
          ├── A subscribes → try_lock(A) → Err → DROPPED         │  busy
          └── B subscribes → try_lock(B) → Err → DROPPED         │  8s
 t=8s   A's tool returns ────────────────────────────────────────┘

 With a blocking lock the emit site would wait those 8s — and every
 other tool call in the batch waits behind it. Dropping is only
 acceptable because the return value is ignored anyway (§3); this is
 the load-bearing link between the two decisions.
```

### 4.1 Two new exports, one new world

```wit
/// `extension-commands` plus lifecycle event delivery.
world extension-events {
    include extension-commands;

    /// Which events this plugin WANTS, as a JSON array of names:
    ///   ["pre_tool_use", "turn_start"]
    ///
    /// Called once at load. Requesting an event is not the same as
    /// receiving it — see §4.2. Anything not in both this list and
    /// the config's `events` list is never delivered.
    export list-events: func() -> string;

    /// One event. `event` is PI's name for it — `tool_execution_start`,
    /// not the shell layer's `pre_tool_use` (§2.1).
    ///
    /// `payload-json` is byte-identical to what a shell hook receives
    /// on stdin for the same event, so a plugin and a hook see exactly
    /// the same thing.
    ///
    /// The return value is IGNORED (§3). Return `"{}"`.
    export handle-event: func(event: string, payload-json: string) -> string;
}
```

`list-events` is load-bearing, not sugar. Without a declared
subscription the host crosses the WASM boundary for every event of
every turn for every loaded plugin, when the typical plugin wants one
or two. It also gives `/tools` (and a future `/extensions`) something
honest to print: *this plugin watches your prompts*.

**Why a third world, and why a ladder.** WIT cannot express an optional
export, which is why `extension` and `extension-commands` are already
separate. A third axis would make the set a lattice — tools,
tools+commands, tools+events, tools+commands+events — and then eight
worlds after the next feature. Keep it a **linear ladder**:

```
extension  ⊂  extension-commands  ⊂  extension-events
```

An events-but-no-commands plugin therefore stubs `list-commands` /
`execute-command` with two-line returns. That is the accepted cost.
The alternative — one wide world with documented stubs — breaks every
existing plugin's source on upgrade, which is precisely what the
original two-world split was created to avoid. The host is indifferent
either way: it already resolves optional exports with
`get_typed_func(...).ok()`.

### 4.2 The config grants; the plugin only asks

```toml
[[extensions]]
path = "~/.nanopi/extensions/watcher.wasm"
events = ["pre_tool_use"]     # absent or empty ⇒ nothing delivered
```

Delivery requires the event to be in **both** `list-events` and
`events`. The plugin declares intent; the user grants it. A plugin
requesting an event it was not granted is reported at load, not
silently dropped — a plugin that appears broken should say why.

This inversion matters more here than for `allow_fs` or
`allow_network`, and §5.1 is the reason.

### 4.3 Host-side shape

At each existing `run_hooks` call site, after the shell hooks resolve:

```rust
for plugin in event_subscribers(event) {   // both-lists filter, precomputed at load
    match plugin.bridge.try_lock() {       // never waits
        Ok(mut guard) => {
            // Separate, much smaller epoch budget than a tool call.
            let _ = guard.handle_event(event.as_str(), &payload_json);
        }
        Err(_) => log::debug!("{}: busy, {event} dropped", plugin.name),
    }
}
```

Notes that are load-bearing:

- `event_subscribers` is precomputed at load, so an event with no
  subscribers costs a slice check, not a lock or a JSON serialization.
- The payload JSON is built **once** per event and shared by every
  subscriber, including the shell hooks.
- The result is discarded, so a malformed return, a trap, and a
  timeout are all the same non-event. A trap still rebuilds the
  instance (existing behavior) so the plugin's tools keep working.

## 5. What will bite

### 5.1 Security — the largest change in the capability model

Today a plugin sees only what the model chose to hand it as tool
arguments. A `pre_tool_use` subscriber sees **every tool call's
arguments**, and a `user_prompt_submit` subscriber sees **every prompt**.
Combined with `allow_network = true`, that is an exfiltration channel
the current model never contemplated.

Consequences for the implementation:

- The grant lives in config, never in the plugin (§4.2).
- `events` + `allow_network` together deserve a startup warning of the
  same kind `url_allowlist = ["*"]` now gets. A plugin that watches
  your prompts *and* can reach any host is worth one line of stderr.
- `/tools` should show subscriptions, so the inventory answers "what
  is watching me" and not only "what can the model call".

### 5.2 Frequency

All eleven current events are per-turn or per-tool-call, so all eleven
are safe. This is a property of today's event set, not a guarantee —
`message_update` and `tool_execution_update` (§2) must stay
undeliverable to plugins, and any future per-delta event inherits that
rule. Write it down at the emit site, not only here.

### 5.3 The epoch budget must be smaller

A tool call is something the user asked for and is waiting on; an event
fires on the critical path of every turn. Reusing the ~30s tool budget
would let a plugin add 30s to every loop iteration. Events get their
own budget — **start at 2s** — and exceeding it is advisory: log and
continue, never fail the turn.

Note the existing caveat still applies: epoch interruption instruments
guest code and cannot interrupt a host function already running, so a
plugin blocked in `host-http-get` is bounded by that function's own
10s timeout, not by the event budget. An event handler that fetches is
therefore bounded by ~12s, not 2s. Plugins should not fetch from event
handlers; say so in the WIT doc.

### 5.4 Head-of-line blocking, and why `try_lock` is the answer

`pre_tool_use` fires before `tool.execute` acquires anything, so there
is no lock cycle and no deadlock. But with parallel tool execution,
plugin A can be mid-`execute` (holding its bridge lock) when A's
`handle-event` is invoked for plugin B's tool call. A blocking lock
would make the event wait out A's entire tool budget.

`try_lock` + drop is correct *only because* events are advisory (§3).
This is the load-bearing link between the two decisions: if veto is
ever added, this line has to change at the same time, and the
second-instance design in §3 is what it changes to.

## 6. Out of reach, deliberately

These need **imports** (host functions), not exports, and each is a new
capability to gate. Not v0.12:

- UI — `setWidget`, `setFooter`, overlays, custom tool renderers,
  autocomplete providers. This is most of PI's 1713 lines of extension
  types, and a TUI surface for guests is the opposite of a ~4 MB static
  binary. Treat as permanently out of scope.
- `sessionManager` read access.
- `before_provider_request` / `before_provider_headers` payload
  mutation (needs the emit sites from §2 first).
- `setActiveTools`, dynamic tool registration mid-session.

The one cheap follow-on worth naming: a single import,
`host-session-append(custom-type, json)`, which is what PI's
`pi.appendEntry` does. It is what lets an event-watching plugin persist
what it observed across `/resume` instead of re-deriving it, and it
composes with this note's design rather than extending it.

## 7. Reference: the eleven events, both subscribers

Facts verified against `src/agent/hook.rs` and `src/agent/loop_.rs` at
the time of writing. Names are post-rename (§2.1).

| # | event | fires | shell hook can | WASM can | `matcher` tested against |
|---|---|---|---|---|---|
| 1 | `tool_execution_start` | before each tool call, ahead of `tool.execute()` | **Block + Transform** (rewrite args) | observe | tool name |
| 2 | `tool_execution_end` | after the tool returns | **Transform** (rewrite `content` / `is_error`) | observe | tool name |
| 3 | `input` | before the user message enters context | **Block + Transform** (rewrite the prompt) | observe | `""` — only `*` can match ⚠ |
| 4 | `before_agent_start` | top of each turn, before the user message is pushed | **Block** (early return) **+ Transform** | observe | turn number |
| 5 | `turn_start` | top of each agent-loop iteration | advisory (Block logged, not enforced) | observe | turn number |
| 6 | `turn_end` | bottom of each iteration, after tool calls | advisory | observe | turn number |
| 7 | `message_end` | after the loop, before post-turn compaction | advisory | observe | turn number |
| 8 | `session_start` | session established | advisory | observe | session id |
| 9 | `session_shutdown` | session torn down — `quit`/`new`/`resume`/`fork`/`import` (§2.2) | advisory | observe | session id |
| 10 | `session_before_compact` | inside `compact_now`, before compaction | advisory (**cannot cancel**) | observe | reason: `threshold`/`manual` |
| 11 | `session_compact` | after compaction succeeds | advisory | observe | reason: `threshold`/`manual` |

**Coverage is identical: 11 for 11.** Only two columns differ — whether
the subscriber can intervene, and (before §2.1) what the event was
called.

Three things fall out of the table:

**Only 4 events have a real capability gap.** Rows 5–11 are advisory
for shell hooks too, so for seven of the eleven a WASM plugin has
*exactly* the same power as a shell hook — plus state that survives
across calls, which a fresh-process hook cannot have. "Observe-only"
is only a restriction on rows 1–4.

**Row 3's `matcher` is a pre-existing trap.** `input` fires with no
tool name, so `matcher` is tested against `""` and any matcher other
than `*` can never match. The code says so in a comment; someone
writing config from `config.toml.example` will not know. Not introduced
by v0.12 — but worth fixing, and the WASM side sidesteps it entirely by
filtering on the `events` list instead of a matcher.

**One `matcher` field means four different things** — tool name, turn
number, session id, compaction reason. That is the price the shell
layer pays for one field across eleven events. The WASM side does not
inherit it: `events` is a name whitelist, with no matcher concept. If
per-tool filtering is ever wanted there, design it fresh rather than
copying this ambiguity.

## 8. Why nanopi keeps the shell layer PI dropped

PI folded `hooks/` into extensions (§2.1) and was right to, for PI. The
same move in nanopi would land differently, for three reasons measured
on this tree:

**1. The WASM runtime is opt-in and costs 3 MB.** Measured, musl
release:

| build | size |
|---|---|
| `cargo build --release` | 4,500,160 B ≈ 4.3 MiB |
| `--features wasm` | 7,576,800 B ≈ 7.2 MiB |
| delta | **+3.08 MB, +68%** |

That is wasmtime, and it is why `[[extensions]]` is ignored with a
warning in the stock binary. Making WASM the only extension mechanism
means either shipping wasmtime by default — which retires the "~4 MB
static binary" that is nanopi's entire reason to exist — or shipping a
default binary with no extensibility at all. PI has no equivalent
cost: an extension is a `.ts` file and Node is already there.

**2. Removing hooks would remove nanopi's only veto.** WASM is
observe-only (§3), so hooks are the only thing that can refuse a tool
call — `check-rm-rf.sh` and its kind. Deleting the shell layer forces
reversing §3, which reintroduces the blocking-lock problem of §5.4 and
its second-instance fix. The two decisions are coupled: cutting one
mechanism makes the other more complex, not less.

**3. The migration is not a like-for-like step.** PI's was: drop a
`.sh` → drop a `.ts`. nanopi's would be: 3 lines of bash → install a
Rust toolchain, add the `wasm32-wasip1` target, `cargo build`,
`wasm-tools component embed`, `wasm-tools component new`, *and* rebuild
nanopi with a non-default feature flag. On the machine nanopi is built
for — the one with no runtime — `/bin/sh` is present and a
cross-compile toolchain is not.

So the shell layer's charter is **not** "PI has it too". It is: *the
only extension mechanism available on a machine with no runtime, and
the only channel that can refuse.* WASM's charter is: *tools, commands,
and state.* They overlap only in observing events, and §4.0 makes that
overlap one code path rather than two.
