## 0. 环境准备（做一次）

### 0.0 ⚠️ 先确认你手上的二进制是新的

**这是最容易出错的一步。** `dist/` 目录里可能躺着一个旧的
`nanopi-v0.11.0-*` 文件 —— 那是 v0.12 的改动**之前**构建的，用它跑
第 1 章会全部"通过测试地失败"（它照常接受旧配置键，因为那是它出厂时
的正确行为）。

`--version` **区分不了新旧** —— `VERSION` 文件在发布前一直是
`0.11.0`，新旧二进制都自称 v0.11.0。用行为判断：

```bash
mkdir -p /tmp/vcheck/.nanopi && cd /tmp/vcheck
printf '[[hooks.totally_bogus_key]]\nmatcher = "*"\ncommand = "true"\n' \
  > .nanopi/config.toml
NANOPI_HOME=/tmp/vcheck/home <你的二进制> -p "hi"
```

| 结果 | 说明 |
|---|---|
| 拒绝启动，报未知 hook 事件 | ✅ 是 v0.12 的构建，可以往下测 |
| 正常运行并回答 | ❌ 是旧构建，回到 0.1 重新编译 |

这个检查测的是 `deny_unknown_fields` 这个新增行为本身，不依赖具体
哪个键名，所以比直接试 `pre_tool_use` 更可靠。

### 0.1 两种构建

```bash
cd ~/workspace/nanopi
git log --oneline -1     # 确认你在 v0.12.0 分支的最新提交上

# A. 标准构建（无 WASM 运行时）——大多数用例用这个
cargo build --release
cp target/release/nanopi /tmp/nanopi-v012

# B. WASM 构建 —— 第 4、5 章用这个
cargo build --release --features wasm
cp target/release/nanopi /tmp/nanopi-v012-wasm
```

**期望**：两个都编译通过。A 约 4.3 MB，B 约 7.2 MB（差值是 wasmtime）。

> **两次 `cargo build --release` 写的是同一个路径**
> （`target/release/nanopi`），后一次会覆盖前一次。所以上面每次都
> `cp` 到不同名字 —— 否则你会拿着 WASM 构建去测第 1 章，或者拿着
> 无 WASM 构建去测第 4 章然后看到 `entries ignored` 一头雾水。
>
> 下文用 `$NP` 指代标准构建，`$NPW` 指代 WASM 构建：
> ```bash
> export NP=/tmp/nanopi-v012
> export NPW=/tmp/nanopi-v012-wasm
> ```
>
> musl 用户把构建命令改成
> `cargo build --release [--features wasm] --target x86_64-unknown-linux-musl`，
> 产物路径相应变成 `target/x86_64-unknown-linux-musl/release/nanopi`。

### 0.3 干净的测试目录

```bash
mkdir -p /tmp/nptest/.nanopi && cd /tmp/nptest
export NANOPI_HOME=/tmp/nptest/home
```

> **注意**：全程用 `NANOPI_HOME` 指向测试目录，避免污染你真实的
> `~/.nanopi`。每一章开头都会重设 `.nanopi/config.toml`。
>
> **不要把 `NANOPI_HOME` 指向当前工作目录本身。** nanopi 读两个配置：
>
> | 路径 | 角色 |
> |---|---|
> | `$NANOPI_HOME/config.toml` | 全局 |
> | `<cwd>/.nanopi/config.toml` | 项目（覆盖全局） |
>
> 如果 `NANOPI_HOME` 等于 cwd，这两个位置会挨在一起，很容易同时存在
> 两份配置。而 `[[hooks.*]]` 和 `[[extensions]]` 是**累加**不是覆盖 ——
> 两份都会生效，于是一个 hook 触发两次，看起来像 bug。上面的
> `NANOPI_HOME=/tmp/nptest/home` 把全局配置放进子目录，两者不会打架。

### 0.4 ⚠️ 让模型**必须**调工具

第 2 章几乎每条都依赖"模型真的调用了 bash"。但模型会偷懒：
`用 bash 执行 echo hello` 它知道答案是 `hello`，很可能直接用文本回答，
**一次工具调用都不发生**，于是你的 hook 看起来"没生效"。

**怎么判断有没有真的调工具**：`-p` 模式下每次工具调用都打两行标记。

```
[bash call_01a066ad] echo hello            ← 调用
[bash → call_01a066ad  10 bytes  1ms]      ← 结果
```

**一行标记都没有 = 模型没调工具**，这条用例的结论无效，换提示词重跑。

**不容易被偷懒的提示词**
```bash
$NP -p "用 bash 执行 date +%s，只回复命令的原始输出"
$NP -p "用 bash 执行 cat /etc/hostname"
```
共同点：答案**不可能**凭模型的知识得出，必须真的执行。

**完全不依赖模型行为的旁路**：让 hook 自己留痕。
```sh
#!/bin/sh
cat > /dev/null
echo "$(date +%T) fired" >> /tmp/nptest/hook-fired.log
# ……原本的 decision 输出
```
`cat /tmp/nptest/hook-fired.log` 有记录 = hook 被调用过。这样把"模型愿
不愿意调工具"和"hook 有没有生效"两件事分开，排障快得多。

## 2. shell hook 的否决与改写

### T2.1 `exit 2` 阻断工具调用，stderr 成为理由

**步骤**
```bash
cd /tmp/nptest
cat > /tmp/nptest/veto.sh <<'EOF'
#!/bin/sh
cat > /dev/null
echo "policy: bash is not allowed in this session" >&2
exit 2
EOF
chmod +x /tmp/nptest/veto.sh
cat > .nanopi/config.toml <<'EOF'
[[hooks.tool_execution_start]]
matcher = "^bash$"
command = "/tmp/nptest/veto.sh"
EOF
$NP -p "用 bash 执行 ls"
```

**期望**
- bash **没有真的执行**
- 模型收到的工具结果是 `blocked by hook: policy: bash is not allowed in this session`
- 模型据此回复（通常会说被策略拦住了）

结果：**☑通过** ☐失败 —— bash 未执行；屏幕 `[bash blocked: policy: bash is not allowed in this session]`；模型明说是「策略钩子」拒绝、「不是沙箱或环境问题」，并主动提出改用 `ls` 工具。（注：显示措辞是 `[bash blocked: …]`，不是本文原先写的 `blocked by hook: …`；模型收到的那份是自解释的长消息）

---

### T2.2 JSON 形式的阻断

**步骤**：把 `veto.sh` 换成
```sh
#!/bin/sh
cat > /dev/null
echo '{"decision":"block","reason":"refused by json decision"}'
```
（注意：走 stdout，退出码 0）

**期望**：同样阻断，理由是 `refused by json decision`。

**为什么重要**：证明两种表达方式都生效，而不只是退出码那条路。

结果：**☑通过** ☐失败 —— 退出码 0 走 stdout 也照样阻断，理由 `refused by json decision`，模型同样归因到 hook 策略

### T2.3 改写工具参数

**步骤**
```bash
cd /tmp/nptest
cat > /tmp/nptest/rewrite.sh <<'EOF'
#!/bin/sh
cat > /dev/null
echo '{"decision":"allow","updated_input":{"command":"echo REWRITTEN"}}'
EOF
chmod +x /tmp/nptest/rewrite.sh
cat > .nanopi/config.toml <<'EOF'
[[hooks.tool_execution_start]]
matcher = "^bash$"
command = "/tmp/nptest/rewrite.sh"
EOF
$NP -p "用 bash 执行 date +%s，只回复命令的原始输出"
```

**期望**（v0.12 起，三处都要对）
1. **两个**标记，原始的和改写后的：
   ```
   [bash call_xxx] date +%s
   [bash ↻ call_xxx] echo REWRITTEN      ← 新增，↻ 表示被 hook 改写
   [bash → call_xxx  10 bytes  1ms]
   ```
2. 实际输出是 `REWRITTEN`，不是时间戳。**字节数不是 10** —— 结果里带了第 3
   点那句 `[note: …]` 前缀，实测 181 字节。数字会随提示词变，别拿它当断言
3. 模型**不会**困惑。它拿到的结果前面带一句
   `[note: a tool_execution_start hook rewrote the arguments of this call
   to {...} — the output below is from those arguments, not the ones you
   sent]`，所以它会直接说"参数被 hook 改写了"，而不是猜有 sandbox

**为什么要检查第 3 点**：这是手工测试发现并修掉的缺陷（`363916b`）。
修复前标记显示的是模型请求的命令、实际跑的是另一个，模型看到自己的
请求被换了答案，编出一个 sandbox 理论并浪费一轮去验证。改写能力从
v0.9.1 就在，但没人在真实模型下试过，所以一直没被发现。

> **交互模式下不一样**：TUI 的卡片是等结果才画的，所以标题会**就地
> 纠正**成 ` ↻ bash  echo REWRITTEN`，只有一行，不像 `-p` 那样两行。

结果：**☑标记 ☑输出 ☑模型不困惑** —— 两行标记都在（`[bash toolu_01]` 然后 `[bash ↻ toolu_01] echo REWRITTEN`）；实际输出是 `REWRITTEN`；模型逐字说出「被一个 `tool_execution_start` 钩子将参数改写成了 `echo REWRITTEN`」，没有编造 sandbox 理论。字节数 181 而非 10，原因见上（`[note: …]` 前缀计入）

### T2.4 hook 崩溃 = 放行（fail-open），且有 stderr 提示

**步骤**
```bash
cd /tmp/nptest
cat > .nanopi/config.toml <<'EOF'
[[hooks.tool_execution_start]]
matcher = "*"
command = "/nonexistent/path/to/hook.sh"
EOF
$NP -p "用 bash 执行 cat /etc/hostname" 2>&1 | grep -i "hook exited"
```

**期望**
- 工具**照常执行**（放行）—— 这是文档承诺的 fail-open 契约
- stderr 有一行点名退出码并给出修法：
  ```
  nanopi: ToolExecutionStart hook exited 127 (127 = command not found —
  check the path) with no decision — allowing the call.
  command="/nonexistent/path/to/hook.sh" stderr="bash: line 1: …: No such
  file or directory"
  ```

**为什么重要**：这条的期望原本写错了，而错误的期望挖出了真问题。

nanopi 通过 `bash -c` 跑 hook，所以路径写错**不会**让 spawn 失败 ——
bash 正常启动、找不到脚本、以 127 退出。127 既不是 2 也不是 JSON
decision，于是落进"其他一切 = 放行"分支，**修复前一个字都不打**。三种
最常见的配错全在这个分支里：

| 情况 | 退出码 |
|---|---|
| 路径写错 / 文件不存在 | 127 |
| **忘了 `chmod +x`** | 126 |
| 脚本自己出错 | 1 |

也就是说：装一个 `check-rm-rf.sh` 却忘了加执行权限，得到的是**零保护
加零提示**。Claude Code 的协议本身也把"非 0 非 2"当错误，所以静默放行
连协议都没对齐。修复见 `hook.rs`；仍然放行（把配错变成拒绝会让一个笔误
卡死每次工具调用，比 fail-open 更糟），改的只是"不再沉默"。

结果：**☑工具执行了 ☑有警告且点名退出码** —— 工具照常执行（`[bash → toolu_01  20 bytes  5ms]`）；stderr 逐字命中 `nanopi: ToolExecutionStart hook exited 127 (127 = command not found — check the path) with no decision — allowing the call. command="/nonexistent/path/to/hook.sh" stderr="bash: line 1: …: No such file or directory"`。

> ⚠️ **本文原先给的 `grep -i "failing open"` 匹配不到任何东西** —— 实际措辞是 `allowing the call`。步骤里的 grep 已改成 `hook exited`。

### T2.5 多个 hook：第一个 Block 短路

**步骤**
```bash
cd /tmp/nptest && rm -f /tmp/nptest/second.log
cat > .nanopi/config.toml <<'EOF'
[[hooks.tool_execution_start]]
matcher = "^bash$"
command = "sh -c 'cat >/dev/null; echo first-blocked >&2; exit 2'"

[[hooks.tool_execution_start]]
matcher = "^bash$"
command = "sh -c 'cat >/dev/null; echo SECOND-RAN >> /tmp/nptest/second.log'"
EOF
$NP -p "用 bash 执行 ls"
cat /tmp/nptest/second.log 2>/dev/null || echo "(文件不存在 = 正确)"
```

**期望**
1. 阻断生效，工具没执行
2. `second.log` **不存在** —— 第二个 hook 没跑。**这条是本用例的重点**，
   不要漏掉那句 `cat`：只看到"被拦了"证明的是 T2.1，不是短路
3. 模型收到的结果说明了机制，而不是让它猜：
   ```
   blocked by a user-configured `tool_execution_start` hook — this is a
   policy refusal from the user's nanopi configuration, not a sandbox or
   environment failure. Hook's reason: first-blocked
   ```
   所以模型应当直接转述"某个 hook 按策略拒绝了"，而**不该**去猜 sandbox、
   也不该去翻 `.claude/settings.json`（那是别的产品的配置）

**为什么加第 3 点**：手工测试中模型两次编造了环境拦截器理论。根因是
系统提示里**从未提及 hook 的存在**（`system_prompt.rs` 里 "hook" 命中
为 0），所以 `blocked by hook: X` 里的 "hook" 对它是个没有定义的名词。

### T2.8 🆕 `message_end` 现在带模型的回复原文（对现有脚本是行为变更）

**这条是 v0.12 stage 5，且它改的是 shell hook 也在用的载荷。**在此之前
`message_end` 的 `arguments` 只有 `{turn_count, response_length}` —— 一个
长度。插件因此能看到用户说了什么（`input`）、每次工具结果
（`tool_execution_end`），却**永远看不到模型说了什么**，所以「记住用户的
偏好」做得到、「记住结论是什么」做不到。

**步骤**
```bash
cd /tmp/nptest && rm -f /tmp/nptest/msgend.json

matcher = "*"
command = "cat >> /tmp/nptest/msgend.json"

```

**期望**：`arguments` 有四个键 ——

| 键 | 期望 |
|---|---|
| `turn_count` | 轮次号 |
| `response_length` | **整段回复**的字节数 |
| `response` | 回复原文 |
| `response_truncated` | `false` |

**关键：`response_length` 保持旧含义。**它是整段的长度，**不是**
`response` 字段的长度。今天读这个数的脚本在升级后读到同一个数字 —— 这是
故意的向后兼容取舍，而不是顺手。截断发生时它也正是「本来有多少」的那个
字段。

**再测截断**：让模型输出一篇长文（超过 16 KiB，例如「把 UTF-8 的历史、
编码规则、与 UTF-16 的对比写详细，至少 6000 字」），然后：

```bash

a=d['arguments']
print('truncated:', a['response_truncated'])
print('response_length:', a['response_length'])

```

**期望**：`response_truncated: true`，`response_length` **大于**
`len(response)`，且 `response` 结尾带

**为什么截断要三重声明**（`response_truncated` 字段、两个长度不相等、以及
文本里的带内标记）：只看 `response` 是最自然的用法，而只看 `response` 的
消费者**绝不能**在没看到「这句话被切断了」的情况下从半句话下结论。带内标
记是三者里唯一挡得住这件事的。这是 invariant 9（绝不让订阅方相信一件没
发生的事）用在载荷上而不是 import 上。

**⚠️ 升级注意，请确认这对你可接受**：载荷按契约由 shell hook 和 WASM 插

`[[hooks.message_end]]` 脚本从收到一个长度变成收到整段回复**。如果你有脚
本按字节数计费、或把 `arguments` 整体塞进日志，请检查一遍。

结果：**☑通过** ☐失败（请描述）

**截断**：`response_truncated: true`、`response_length: 99173`、`len(response): 16435`，且结尾带 `[nanopi: response truncated, 16384 of 99173 bytes]` —— **三重声明齐全**，且 `response_length` **大于** `len(response)`，保持「整段有多少」的旧含义。`16435 = 16384 + 51`，与「标记计在上限之外」的设计一致（`hook.rs` 的 `truncate_response`）。

**升级影响已确认可接受**：这确实是 shell hook 载荷的行为变更，已写入 release notes 的 Compatibility 一节（最可能受影响的是「把 `arguments` 整体塞进日志」或按字节计费的脚本）。

```bash
# 会话里执行 /resume，选一个不是 A 的会话，记下横幅里的 id，记作 B
# 随便聊一句，然后 /quit
```

**期望**
- 退出时只有**一行** `To resume: nanopi --continue    or    nanopi
  --session <id>`，里面的 id 是 **B**，不是 A
- 照着这条命令跑一次，恢复出来的是你刚才聊的那段对话
- 上面**不再有** `✓ session <前8位> saved` 那一行

**为什么重要**：`tui.rs:365` 绑定的 `header` 从不重新赋值，而 `/new`、
`/resume`、`/fork`、`/import` 只更新 `app.session_id`。修复前，凡是中
途切过会话的运行，退出提示给的都是**启动时**那个会话 —— 复制粘贴那条
`--session` 命令会把你送回一段已经放弃的对话，而且当时看不出哪里不对，
因为两个都是合法 UUID。

发现于 T3.5 的人工测试：hook 报 `01a06aac`（正确），退出行报
`01a06ac1`（启动会话）。

那行 `✓ session <前8位> saved` 一并去掉了：截断正好停在第一个 `-` 前一
位，`01a06af4-a1e9-…` 印出来是光秃秃的 `01a06af4`，看着像一个完整 id，
而下一行就是完整的那个。v7 的前几位是时间戳高位，同一天的会话只差最
后几位 —— 等于让眼睛去做它最不擅长的比对。完整 id 已经在下面了。

自动化覆盖：**无**。这两行印在一个几百行 async 函数的末尾，没有可以
注入假 App 的接缝；抽一个 `closing_lines(sid)` 出来只能断言格式，断言
不了调用点传的是哪个变量 —— 而传错变量正是这个缺陷本身。

结果：**☑通过** ☐失败 —— 启动会话 A=`01a07fdb-3ea5-…`，`/resume` 进入 B=`01a07fd4-256b-…`；退出行给的是 **B**；`To resume` 只有**一行**；`✓ session … saved` 那行**已不存在**。照着 `--session 01a07fd4-…` 跑，恢复出的正是刚才那段（答出了 `蓝色`）

### T3.8 流式输出中途插话不会凭空消失

降级路径，一直是好的。本用例测的是发送**成功**但没人来取。

发现于 dist/4.jsonl + 人工测试：会话文件里只有 `who are you` 和它的

结果：**☑通过** ☐失败 —— 屏幕出现 `[steer] 你是谁`；本轮结束后**自动**开了新一轮回答它；会话文件里两问两答**都在**，没有伪造历史

### T4.7 TUI 里的 stderr 提示不再阶梯状错位

**步骤**
```bash

cat > .nanopi/config.toml <<'EOF'

```

`[wasm:trace]` 行会连续打出好几条。

**期望**：每一行都从**第 0 列**开始。

**修复前的样子**（第二行从第一行结束的那一列开始）：
```
[wasm:trace] events-plugin: observed input
                                          [wasm:trace] events-plugin: observed turn_start
```

**为什么重要**：TUI 运行时终端处于 raw mode，`\n` 只做换行不做回车 ——
光标下移一行、列不变。程序里散落 35 处 `eprintln!` 都有这个毛病，不只
插件日志：流式重试提示、hook 诊断、`/model` 切换的 vendor 警告、
`/new` 重读配置的告警。现在统一走 `crate::note!`（`render/raw_tty.rs`），
raw mode 下自动补 `\r`。

**曾经仍未修的部分，现已修复**：这些提示原先绕过 ratatui 的
`insert_before`、写在它管理的区域里，所以下一次重绘就抹掉了 —— 你看到的
是个一闪而过的中间态。

现在 TUI 占据屏幕期间 `note` **完全不写 stderr**：它推入一个进程级队列，
TUI 主循环每 tick 用 `insert_before` 排空进滚动区，和 `wasm::notify` 为
同一个理由用的是同一形状。35 个调用点一处未改 —— 它们共用 `note!`，所
以修的是那一处。

**所以本条要多验一步**：提示打出来之后**再让屏幕重绘一次**（随便按个键、
或等下一次流式输出），确认那几行**还在**，而不是只在出现的瞬间可读。

两种没有排空者的情形也处理了，不是假设掉：退出流程会在 raw mode 已经关闭
的状态下把仍在队列里的内容冲到 stderr；而一个不再 tick 的循环也无法让队

### T5A.5 重载期间的 `plugin_context` 贡献

**步骤**：需要一个申请 `allow_context` 的插件。**两个示例插件都不申请**，
所以这一条**人工跑不了**，如实记为「自动化覆盖」。

规则（`Agent::reload_extensions` 文档注释）：

| 状态 | 跨 `/reload` |
|---|---|
| `host-store` 文件 | **存活** —— 那是插件跨**重启**的持久化，重载把它擦掉等于让 `/reload` 意外变成破坏性命令 |
| `plugin_send` 的循环护栏 + 已花掉的会话预算 | **存活** —— 否则这个上限就能被「那个可以建议用户 /reload 的插件」自己重置 |
| `plugin_context` 贡献，插件仍加载且**仍持有** `allow_context` | **存活** |
| 同上，但插件已消失、或重载后**没有**该 grant | **丢弃**，且报告行**点名每一个**被丢弃的贡献 |

最后一条是本轮的修正。旧注释以「丢弃会静默停掉一个已加载插件的能力、除了
重启没法恢复」为由主张存活 —— 那个论证说的是插件**还在、grant 还在**的情形。
另外两种情形下保留会把同一个抱怨反过来：一段署名为某扩展的文字会留在模型的
system prompt 里，而没有任何东西能撤回它，同样得重启。

自动化覆盖：`a_contribution_survives_a_reload_with_the_grant_and_is_dropped_without_it`
和 `a_plugin_that_fails_to_reload_keeps_its_previous_instance`
（`src/agent/build.rs`）。

结果：**☑自动化覆盖（人工不可达，已确认原因）** —— 两个示例插件都不申请 `allow_context`，因此人工无法构造贡献。已核对自动化用例确实存在并通过：`a_contribution_survives_a_reload_with_the_grant_and_is_dropped_without_it`、`a_plugin_that_fails_to_reload_keeps_its_previous_instance`（`src/agent/build.rs`）

### T5A.6 换实例时正在飞的调用：带内拒绝

**步骤与结论**：`src/wasm/loader.rs` 里有**两种不同的措辞**，是刻意分开的：

| 函数 | 场景 | 措辞要点 |
|---|---|---|
| `staleness` | 调用**还没进入** guest 就被拒 | `was replaced by /reload — this call was refused rather than run against the instance it was loaded from` |
| `staleness_after_running` | 调用**已经进入** guest，重载才落地 | `was replaced by /reload WHILE this call was running`，结果**被丢弃**，但**已经产生的副作用仍然成立**，并且明确告诉用户 |

第二种为什么要单独措辞：它**跑过了**。把它的结果算作现在这个插件的，正是
这整套机制要防的那个「静默撒谎」；但它已经做过的事（写了文件、发过 HTTP、
写过 store key）已经发生了，必须说出来，而不能让用户以为什么都没发生。

**这一条人工触发不了，而且是设计使然**：`/reload` 在**有轮次正在进行时本身
就不换任何东西** —— agent 在一轮期间被移出 slot（见 T5A.7），所以
`/reload` 落不下去。带内拒绝是给「早先发出去的 `Arc<dyn Tool>` 克隆」兜底的
纵深防御，不是日常路径。

自动化覆盖（打在真实 fixture 上，不是打在 `Err` 上）：
`a_replaced_bridge_refuses_instead_of_running_the_old_instance`、
`a_replaced_bridge_refuses_commands_too`、
`a_replaced_bridge_receives_no_more_events`
（`tests/wasm_plugin_integration.rs`，其中 1322 行断言
`WHILE this call was running`）。

### T5A.7 🆕 轮次进行中的 `/reload` 不能污蔑配置

**步骤**
```bash

```
TUI 里：

extension 报告会落进「配置没解析」那个分支，于是对一份**完全正常**的配置

它当场还自相矛盾：下一行就是 `no warnings`，因为本该解释这次解析失败的注释
没有东西可解释。

**对照组不能省**：只看轮次中那一条，一个「永远说 in flight」的实现也能过。

结果：☐通过 **☒失败 → 本轮已修**

**这条是写这一章时新发现的缺陷**，也是它被加进来的原因。用**同一份配置**做对照：

| 时机 | 报告行 |
|---|---|
| 轮次进行中 | `… · extensions unchanged (config.toml did not parse)` |
| 空闲 | `… · 1 extension(s) reloaded (3 tool(s), 0 command(s))` |

配置是合法 TOML（`tomllib` 能解析，启动也接受它）—— 那句话**是假的**。根因：agent 在一轮期间被**移出** slot，`handle_reload` 里那个 `if let Some(a) = g.as_mut()` 整块被跳过，skills / hooks / extensions **全都没重载**，而缺失的 extension 报告落进了「配置没解析」那个 `None` 分支。它当场还自相矛盾：紧接着就印 `no warnings`，因为本该解释这次解析失败的注释根本没有东西可解释。

后果是把用户送去查一份没问题的 TOML，而真正的答案是「等这一轮跑完」。这也正好违反了这行字自己的设计原则（代码注释里写着「the line always states what it did NOT do」）—— 它确实说了没做什么，但**说的理由是假的**。

**已修**（`afca688`）：新增 `agent_busy` 分支，输出 `nothing reloaded (a turn is in flight — run /reload again once it finishes)`。`handle_reload` 没有测试接缝（`Term` 是 `Terminal<CrosstermBackend<Stdout>>`，不是 `TestBackend`），所以把这段判断抽成纯函数 `reload_extensions_clause` —— 缺陷本来就在这段判断里。三个测试：busy 分支点名轮次、真正的解析失败**保留自己的措辞**（防止修复退化成「把解析失败也改口」）、有报告时报告优先。

### T8.2b 中途杀掉进程后，会话仍能恢复 ⭐

**前提**：能开两个终端，或者知道怎么发 `SIGKILL`。

**步骤**
```bash
cd /tmp/nptest && rm -f .nanopi/config.toml

# 让它跑一个长命令，例如：用 bash 执行 sleep 300
# 趁工具还在跑，从另一个终端 kill -9 掉 nanopi（不要用 Ctrl-C，
# 那走的是正常取消路径）
tail -2 ~/.nanopi/sessions/<刚才那个 id>.jsonl   # 应以 tool_call 结尾，没有 tool_result

```

**期望**

- 启动时有一行提示：`this session had 1 tool call(s) with no recorded
  result — nanopi most likely exited while they were running…`
- 模型的回答会说**结局未知**，不会声称命令失败，也不会编一个结果

**为什么重要**：`tool_call` 是在工具执行**之前**落盘的（这个顺序是对的
—— 对 `bash` 来说「什么命令即将执行」比结果更值得记录，因为副作用可能
已经发生）。但这留下一个窗口：进程在长命令期间丢失，文件末尾就是一个
没有结果的孤儿 `tool_call`。

原样回放出来是一个带 `tool_use` 但无人应答的 assistant 消息，两家 API
都拒绝 —— 那个会话**永久无法恢复**，而且报错是 provider 的 400，指不到
真正原因。偏偏这最容易发生在你为了打断长命令而按 Ctrl-C 的时候。

修法照 PI 的 `tool-durability.md` 不变式 9：合成一个结果，**明说结局
未知**。不说「失败」—— 那在最要紧的情形下是假话，命令很可能已经跑完了。

结果：**☑能恢复 ☑有提示 ☑模型不臆测** —— 三项全对。

- 会话文件末尾确实停在一个没有 `tool_result` 的孤儿 `tool_call`（3 条记录）
- `--continue` 正常启动并作答，退出码 0，**不是** provider 400
- 提示逐字命中：`nanopi: this session had 1 tool call(s) with no recorded result — nanopi most likely exited while they were running. Synthesized unknown-outcome results so the session can be resumed; the model is told the outcome is unknown rather than being given a made-up one.`
- 模型没有声称失败、也没编结果，而是**去查**（`ps -ef | grep '[s]leep 300'`），发现那个 `sleep` 还在跑、已被 init 收养，如实汇报并问要不要杀掉

> ⚠️ **杀进程的方式会决定这条测不到东西**：先 `pkill -P` 杀子进程会让 bash 退出、nanopi 从容写下 tool_result，孤儿就不存在了。必须**只**对 nanopi 本身发 `kill -9`。

### 缺陷 4 值得单独看一眼

它是本轮唯一会让用户**丢结果**的缺陷，而且它躲过了两层防线：

- **T4.4 本条的断言是通过的。**「两张卡片各有标题」画对了，工具也都跑完了 ——
  失败发生在那之后，模型一个结果都没看到。只按本条的勾选项走会记成通过。
- **自动化用例也是绿的。**`a_parallel_tool_batch_reports_each_call_separately`
  打在一个假的 OpenAI 端点上，而这是 Anthropic 传输独有的消息组装问题；
  而 `tool_result_block_serializes_with_is_error` 把所有 user 消息的 content
  拍平后再断言，两种形状都能过。

新回归测试改断**user 消息的条数**和**每条里的 block 数** —— 那才是区分两种
形状的地方。

### 缺陷 7（未修）的详情与建议

`settings.toml` 里的 `thinking_level` 只被 `/settings` 界面用来**显示和循环**，
并会写回磁盘；但 `App` 恒以 `thinking: None` 初始化，`main.rs` / `mode/print.rs`
里**一次都没读过**这个字段（`grep thinking_level src/` 只命中 `settings_toml.rs`
和 `mode/tui.rs` 的界面代码）。所以：

- 在 `/settings` 里把思考档位调好、退出、再进来 —— 设置**没有恢复**
- `-p` 模式下**完全没有**开启思考的途径（也没有命令行开关）

这是「有写无读」，和 `ModelChange` 当年「有读无写」是同一族的缺陷，也是
`docs/claims-and-races.md` 那类清单该收的条目。**本轮没有动它，因为它需要一个
决定而不是一个补丁**：`settings.toml` 的档位该不该覆盖 `-p` 模式？会话中途用
`Shift+Tab` 改过之后，下次启动是听磁盘的还是听会话的？优先级定了再改，几行就够。

顺带记一条同类观察（**不是缺陷**，只是名单该维护）：
`supports_thinking_rejects_older_and_unknown` 断言 `claude-haiku-4-5`
**不**支持 thinking，但直连该端点实测它返回 `thinking` 内容块。那条断言看起来
是刻意写的，所以本轮没有擅自翻转 —— 请确认后再定。
