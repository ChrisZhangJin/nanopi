## 1. agent 的编排控制（dispatch / amend / stop / continue）

> 本章测的是**主 agent 通过工具**控制子 agent，不是用户直接控制 ——
> phase 1 revision 之后，用户从不直接操作一个正在跑的 agent。所有步骤
> 都是「让模型去调用 `agent`/`send_message`/`stop_agent`/`list_agents`」，
> 人只是观察结果。

### T1.1 dispatch：单个 agent 跑完并报告

**前提**：TUI 或 `-p`，模型可访问 `agent` 工具。

**步骤**：让模型用 `agent` 工具的 single 模式委派一个小任务（例如
"读 README.md 前 20 行并总结一句话"）。

**期望**：
- `agents` strip（TUI）或 JSON 事件（`-p --output json`）里出现该 agent
- agent 结束后状态变为完成（`✓`），工具结果里是 `report.md` 的内容（见
  `docs/agents.md` "Report" 一节），带一行 `- [x]`/`- [ ]` 的任务项清单

结果：☐通过 ☐失败

---

### T1.2 amend：在 agent 跑的过程中追加指令，下一个 turn 边界生效

**前提**：一个耗时较长、会跑多轮的任务（例如"通读 src/ 下 5 个文件并
逐个总结，每个文件单独一轮"）。

**步骤**：
1. 用 `agent` 以 `background: true` 派出该任务
2. 趁它还在跑，让模型调用 `send_message(id, "再额外检查一下是否有
   TODO 注释")`
3. 等它结束，查看 `report.md`

**期望**
- `send_message` 对一个仍在运行的 agent 的效果是**追加到 brief**（见
  `docs/agents.md` "Brief and amendments"）：子进程轮询 brief（500ms，
  连续两次大小不变才算稳定），在**下一个 turn 边界**把新增内容当成一条
  steering 消息注入，且只注入一次
- `report.md` 的任务清单里出现对应这条 amendment 的 `- [x]`/`- [ ]`
  复选行
- amendment **不会**打断当前正在进行的那一轮；它要到下一轮开始前才
  被子进程看到

结果：☐通过 ☐失败

---

### T1.3 stop：主动停止一个仍在运行的 agent

**前提**：派出一个会跑较久的任务（background 模式）。

**步骤**：agent 还在运行时，让模型调用 `stop_agent(id)`。

**期望**
- agent 状态变为 `stopped`（strip 里是 `■`，见 `docs/agents.md` 的
  glyph 表）
- `stop_agent` 返回后，agent 产出一份**部分** `report.md`（带已完成和
  未完成的任务项区分）
- 主 agent 的当前轮不受影响，继续正常运行

结果：☐通过 ☐失败

---

### T1.4 continue：对一个已经结束的 agent 发消息会把它当新任务续跑

**前提**：先让一个 agent 自然跑完（状态 `✓`）。

**步骤**：让模型对这个已完成的 agent 调用
`send_message(id, "再补充总结一下安全风险")`。

**期望**：根据 `send_message` 工具描述（"If it already finished, it is
continued under the same id with the message as its next task"）——
- 同一个 `id` 被复用，**不**产生新的 agent id
- 该 agent 的状态从 `✓` 变回运行中，再变回 `✓`
- 新的 `report.md` 既反映原任务也反映续接的新任务

结果：☐通过 ☐失败

---

### T1.5 list_agents：枚举当前 run 里的全部 agent

**前提**：至少有 2 个 agent 处于不同状态（一个 `✓`、一个仍在跑或
`stopped`）。

**步骤**：让模型调用 `list_agents`。

**期望**：返回里每个 agent 都带 id、description、state、elapsed、
turns、tokens、report path（对应工具描述的字段列表），且状态与 strip
显示的一致。

结果：☐通过 ☐失败

## 3. `/orchestrator` 模式

### T3.1 裸命令是切换（toggle）

**前提**：TUI，`[experimental] orchestrator` 未设置或为 `false`。

**步骤**：输入 `/orchestrator`，观察状态行；再输入一次 `/orchestrator`。

**期望**：第一次后状态行出现 ` · ⎈ orchestrator` 段；第二次后消失 ——
裸命令是开关切换，不是只能开。

结果：☐通过 ☐失败

---

### T3.2 `on` / `off` 显式设置

**步骤**：`/orchestrator on`，再 `/orchestrator on`（重复开不应有副作用），
再 `/orchestrator off`。

**期望**：第一次和第二次后状态行都显示 `⎈ orchestrator`（重复 `on` 幂等，
不会把 orchestrator 的工具集误当成"原始集"存起来）；`off` 后消失，且
工具集/系统提示还原成关闭前的样子（不是空集或残缺集）。

结果：☐通过 ☐失败

**期望**：打印 `Usage: /orchestrator [on|off]`，开关状态**不变**（既不

### T3.6 会话中途切换不影响正在运行的 agent

**前提**：orchestrator 关闭状态下派出一个耗时的 background agent。

**步骤**：agent 还在跑时，输入 `/orchestrator on`。

**期望**：切换提示为"orchestrator mode on (from next turn)"（下一轮

## 5. worktree 合并与合并冲突

### T5.1 `isolation: "worktree"` 的 agent 完成后自动合并

**前提**：当前目录是一个干净的 git 仓库（无未提交改动）。

**步骤**：让模型用 `agent` 工具派一个 `isolation: "worktree"` 的 agent，
任务是"在一个新文件 `/tmp` 之外的仓库内创建一个新文件并写入一行文本，
然后提交"。

**期望**
- agent 在独立的 git worktree/分支里工作
- 完成后，变更被**自动合并**回主分支/主工作树（无冲突时无需人工介入）
- 合并后 worktree 被移除；工具结果提到了合并结果

结果：☐通过 ☐失败

---

### T5.2 无改动的 worktree 直接被移除

**步骤**：派一个 `isolation: "worktree"` 的只读任务（例如"读几个文件,
不要修改任何东西"）。

**期望**：agent 结束后，由于 worktree 没有任何改动，它被直接删除，
不产生合并动作，也不留下分支。

结果：☐通过 ☐失败

---

### T5.3 合并冲突升级给用户

**前提**：主工作树上先手动改动某一行；再派一个 `isolation: "worktree"`
的 agent，让它改动**同一行**（给它一个会冲突的明确指令）。

**步骤**：等 agent 完成，观察自动合并的结果。

**期望**：自动合并失败（冲突），根据 Phase 4 D-11 的约定：
- 冲突被**升级给用户**，而不是静默丢弃一方改动或自动选边
- 冲突的 worktree 和分支被**保留**，供人工后续处理（不会被自动删除）
- 工具结果/界面里清楚说明发生了合并冲突、分支名和 worktree 路径

结果：☐通过 ☐失败

## 6. 已废弃的用户直控能力：验证其缺席

> Phase 1 的 revision（2026-10-03）把 agent 的运行时换成了
> `nanopi -p` 子进程，由主 agent 通过工具（dispatch/amend/stop/
> list/continue）全权控制；用户不再直接控制一个运行中的 agent。
> 以下两条原本写在 D-10 里的用例，现在反过来验证**它们不存在**，
> 并引用这次 revision 作为依据，防止日后被误当成"忘了实现"而补回去。

### T6.1 不存在用户的"全部停止"（Ctrl+X）

**步骤**：TUI 里派出若干 agent 之后，按 `Ctrl+X`。

**期望**：`Ctrl+X` **没有**绑定到"停止所有 agent"这个动作——它要么是
未绑定按键（无效果），要么绑的是别的、与 agent 控制无关的动作。
`grep -n "StopAllSubagents\|StopAllAgents" src/keys.rs src/mode/tui.rs`
应当找不到任何存活的、仍接到 agent 停止逻辑上的绑定（旧绑定名可能还
在历史提交里，但当前 HEAD 的按键表里不应该有一条指向"停止全部 agent"
的映射）。用户若想停止某个 agent，只能靠要求模型调用 `stop_agent`——
没有旁路。

结果：☐通过 ☐失败

---

### T6.2 不存在逐次调用前的 approve/deny/always 提示

**步骤**：派出一个会多次调用工具的 agent，全程观察 TUI/stdout，
**不要**提前配置任何批准策略。

**期望**：从不出现任何"approve this call? [a]lways/[d]eny/..."形式的
交互式提示——`docs/agents.md` "Agents strip" 一节明确写了
"There is no 'waiting for permission' state: children run with
`--approve` or `--distrust` decided at dispatch and never prompt"
（UI-03）。信任级别在**派发时**一次性决定（`--approve`/`--distrust`
命令行参数，见 `docs/agents.md` "Child command line"），子进程运行全程
不会停下来等待人工批准某一次具体的工具调用。

结果：☐通过 ☐失败

## 附：QA-02 二进制体积

**测量环境**：与里程碑开始前（research A3）同一容器/profile，
`cargo build --release`（标准构建，无 `--features wasm`）。

| 项 | 数值 |
|---|---|
| 里程碑开始前基线（4,881,744 字节的来源提交） | `5ec258f`（`chore(release): bump to v0.12.1`，即本里程碑 phase 1 第一个提交 `60e89d8` 之前的最后一次提交） |
| 基线体积 | 4,881,744 字节 |
| 本轮体积（`stat -c %s target/release/nanopi`） | 4,892,864 字节 |
| 差值 | **+11,120 字节（约 10.9 KiB）** |
| 预算 | ≤ 约 150 KB |
| 结论 | ✅ 远低于预算，未超支，未做任何体积削减 |

**测量命令**：
```bash
git checkout 5ec258f -- Cargo.toml Cargo.lock   # 仅用于历史对照，未在本仓库实际签出
cargo build --release
stat -c %s target/release/nanopi
```
（基线数字 4,881,744 来自 phase 6 research A3 的既有记录，本轮未重新
编译基线提交，只编译了 HEAD 并与该记录做差。）

**Cargo.toml 依赖差异**（`git diff 5ec258f..HEAD -- Cargo.toml`）：

```diff
+# Display-width measurement for soft-wrapping the input box (CJK/wide
+# chars count as 2 columns). Already in the tree via ratatui; pinned
+# here so the wrap math has a direct, stable handle on it.
+unicode-width = "0.2"
```

| 新增 crate | 直接引入还是已在依赖树里 | D-11 理由 |
|---|---|---|
| `unicode-width 0.2` | 已通过 `ratatui` 传递引入；此次只是把它提升为直接依赖并锁定版本 | TUI 输入框需要按**显示宽度**（而非字节数/char 数）折行，CJK 等宽字符要按 2 列计算；没有这个 crate 中文输入会在终端里折错行。由于它已经在依赖树里（ratatui 的传递依赖），直接依赖不增加新的编译单元图，体积增量主要来自新增的折行逻辑本身而非这个 crate |

**体积预算结论**：+11,120 字节远低于 ~150 KB 的预算线，无需收缩
orchestrator 提示文本或做任何其他削减。
