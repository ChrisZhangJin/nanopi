# nanopi v0.5 — Research Notes

> Companion to v0.1. Covers protocol adapter design, agent-loop spec, session/config design, and the hook/yolo/-p designs aligned with Claude Code and Codex conventions.
> Read top-down; each section builds on the last.

## 1. Protocol Adapter Design

### 1.1 The two protocols we must speak

v0.5 must support **both** families, because real users have mixed deployments:
- **OpenAI-compatible** (the dominant standard; DeepSeek, vLLM, ollama, LM Studio, Azure OpenAI Responses, etc.)
- **Anthropic-compatible** (Claude API, plus AWS Bedrock's Anthropic path)

Both are HTTP+SSE but differ in:
- Request envelope (key names, message shape, tool definitions)
- Streaming event names and payload shape
- Tool-calling conventions (function-call vs tool-use)

### 1.2 Wire-format comparison

#### Request envelope

| Field | OpenAI-compatible | Anthropic-compatible |
|---|---|---|
| Endpoint | `POST /chat/completions` | `POST /v1/messages` |
| Auth | `Authorization: Bearer ...` | `x-api-key: ...` + `anthropic-version: 2023-06-01` |
| Model | `model: "..."` | `model: "..."` |
| Messages | `{role, content}` array (content can be string or array of parts) | `{role, content: [{type:"text", text:"..."}]}` |
| System prompt | Either first message with `role:"system"` or absent | Separate top-level `system: "..."` field |
| Tools | `tools: [{type:"function", function:{name, description, parameters}}]` | `tools: [{name, description, input_schema}]` (JSON Schema directly) |
| Tool choice | `tool_choice: "auto"` or `{type:"function", function:{name}}` | `tool_choice: {type:"auto"}` or `{type:"tool", name}` |
| Stream | `stream: true` | `stream: true` |

#### Streaming events

| OpenAI chunk | Anthropic event |
|---|---|
| (no preamble) | `message_start` (carries initial message + id) |
| `choices[0].delta.role` | (already in `message_start`) |
| `choices[0].delta.content` (string deltas) | `content_block_start` (with `type:"text"`) → `content_block_delta` (`{type:"text_delta", text:"..."}`) |
| `choices[0].delta.tool_calls` (array, usually one element) | `content_block_start` (`type:"tool_use"`) → `content_block_delta` (`{type:"input_json_delta", partial_json:"..."}`) → `content_block_stop` |
| `choices[0].finish_reason: "stop" / "tool_calls" / "length"` | `message_delta` (`{stop_reason, stop_sequence}`) |
| `data: [DONE]` | `message_stop` |

**Key insight**: OpenAI coalesces many small deltas into one chunk; Anthropic is event-per-state-change. Our adapter must translate to a **single internal event stream** (see §2.1) regardless.

### 1.3 Internal event stream (the unification)

We define **one** internal type that both adapters produce:

```rust
// crates/nanopi-core/src/event.rs

#[derive(Debug, Clone)]
pub enum AgentEvent {
    /// Stream started; carries the empty assistant message skeleton.
    Start { message_id: String },

    /// Incremental text content.
    TextDelta { content_index: u32, text: String },

    /// Incremental thinking content (Anthropic-specific, OpenAI ignores).
    ThinkingDelta { content_index: u32, text: String },

    /// A complete or partial tool call. The provider adapter buffers
    /// partial_json deltas until the block is closed, then emits one
    /// ToolCall with the full arguments.
    ToolCall { content_index: u32, call: ToolCall },

    /// Stream done, with final usage stats.
    Done { finish_reason: FinishReason, usage: Usage },

    /// Stream errored.
    Error { error: AgentError },
}

#[derive(Debug, Clone)]
pub struct ToolCall {
    pub id: String,                 // OpenAI: "call_xxx", Anthropic: "toolu_xxx"
    pub name: String,
    pub arguments: serde_json::Value,  // already-parsed JSON
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum FinishReason {
    Stop,        // natural end
    ToolCalls,   // model wants to call tool(s)
    Length,      // hit max_tokens
    Refusal,     // Anthropic-only: model refused
    Unknown,
}

#[derive(Debug, Clone, Default)]
pub struct Usage {
    pub input_tokens: u32,
    pub output_tokens: u32,
    pub cache_read_tokens: u32,    // OpenAI cached + Anthropic cache_read
    pub cache_write_tokens: u32,   // Anthropic cache_creation
}
```

**Why this shape**:
- `content_index` mirrors OpenAI's array semantics so we can re-render in TUI without bookkeeping
- Tool args are pre-parsed `serde_json::Value` — adapters do the work, the loop doesn't
- Anthropic-specific things (`thinking`, `cache_*`) are populated when present, otherwise empty

### 1.4 Adapter trait

```rust
// crates/nanopi-core/src/provider.rs

#[async_trait::async_trait]
pub trait Provider: Send + Sync {
    fn id(&self) -> &'static str;        // "openai" | "anthropic" | ...
    fn model(&self) -> &ModelId;
    fn supports_thinking(&self) -> bool;

    /// Stream one assistant turn. Yields AgentEvents until Done or Error.
    async fn stream(
        &self,
        ctx: &Context,
        opts: &RequestOptions,
        tx: mpsc::Sender<AgentEvent>,
    ) -> Result<Usage, AgentError>;
}
```

Both adapters are stateless — they take a `Context` (already converted to provider-agnostic shape) and return a stream of `AgentEvent`s. The **Context** is the same for both providers; conversion happens **out-of-band** in `Context::to_openai()` / `Context::to_anthropic()`.

### 1.5 Context (the unified input)

```rust
pub struct Context {
    pub system: Option<String>,            // optional system prompt
    pub messages: Vec<ContextMessage>,     // alternating user/assistant/tool_result
    pub tools: Vec<ToolSpec>,              // tool definitions (provider-agnostic)
}

pub enum ContextMessage {
    User { content: Vec<ContentBlock> },           // text, image, etc.
    Assistant { content: Vec<AssistantBlock> },    // text, thinking, tool_call
    ToolResult { tool_use_id: String, content: String, is_error: bool },
}
```

Conversion (one method per provider) is a thin mapping. **Provider-specific quirks** belong here, not in the loop:
- Anthropic requires last message to be `user` (we may need to inject a placeholder)
- Anthropic tool result blocks are inside a `user` message with `content: [{type:"tool_result", ...}]`
- OpenAI tool results are separate `role:"tool"` messages

### 1.6 v0.5 implementation scope

**v0.5 ships only OpenAI-compatible.** Anthropic is a v0.6+ effort because:
- Different auth header conventions need careful env-var handling
- Different SSE event choreography is real work
- DeepSeek already proves OpenAI-compat is the workhorse

We **design** the trait so adding Anthropic is purely additive — drop in `AnthropicProvider`, wire it in `ProviderRegistry`.

## 2. Agent Loop Spec

### 2.1 What "the loop" actually does

The agent loop drives one user turn to completion. It owns:
- The current `Context` (mutable across turns)
- The provider (chosen by model id)
- The tool registry (built-in + hooks)
- The session (for persisting events)

A turn goes:
1. `Agent::prompt(messages)` — append user messages to context
2. Call `provider.stream(ctx, opts)` → stream of `AgentEvent`s
3. Persist events to session JSONL as they arrive
4. Render to TUI as they arrive
5. On `Done`:
   - If `FinishReason::ToolCalls`, run each tool (sequentially or in parallel), append `ToolResult` messages to context, **go back to step 2**
   - Otherwise, return to caller; the turn is complete
6. If `Error`, surface to TUI; offer retry / abort

### 2.2 Concurrent architecture (Rust-flavored)

```
┌─────────────────────────────────────────────────────────────┐
│                       Agent::prompt                          │
│                                                              │
│  Loop:                                                       │
│    1. build_request_context()                                │
│    2. provider.stream(ctx, opts, tx)  ─── spawns task ──┐    │
│    3. rx.recv() events:                               │    │
│         - persist to session                       ╔══▼════════════════╗
│         - render to TUI                            ║  Provider task    ║
│         - collect ToolCalls (buffered)             ║  (HTTP/SSE/JSON)  ║
│    4. on Done:                                      ╚═══════════════════╝
│         - if ToolCalls: execute_tools(calls)              ▲
│             - for each call:                             │
│                 - run PreToolUse hooks (see §6)           │
│                 - if blocked → drop, append error result  │
│                 - else: tool.execute(args)                │
│                 - run PostToolUse hooks (post-process)    │
│             - append ToolResult messages to context       │
│             - loop back to step 2                         │
│         - if Stop/Length: return final Usage              │
└─────────────────────────────────────────────────────────────┘
```

**Concurrency model in Rust**:
- `provider.stream(...)` is async; we either `await` directly (simpler) or spawn a task and `select!` against a `Ctrl-C` channel (production-quality)
- Tools that are I/O-bound (bash, read) run in `tokio::task::spawn_blocking` because they may block the runtime
- Tools that are CPU-bound (small JSONL edits) run inline

### 2.3 Streaming-to-TUI

A separate `Renderer` trait abstracts "where do events go":
- `StdoutRenderer` — ANSI escapes, current behavior (v0.1's output)
- `TuiRenderer` — crossterm-backed full TUI (v0.5's new mode)

Both consume the same `AgentEvent` stream. The TUI is **not** in the agent's hot path — it subscribes to a `broadcast` channel that the loop pushes to.

```rust
pub trait Renderer: Send {
    fn on_event(&mut self, event: &AgentEvent);
    fn on_tool_call_start(&mut self, call: &ToolCall) -> ToolHandle;
    fn finish(&mut self);
}
```

`ToolHandle` lets the renderer reserve a region for tool output that gets filled in asynchronously as bash streams.

### 2.4 Cancellation

`Ctrl-C` during a turn must:
- Stop the provider stream (cancel the HTTP request)
- Abort any in-flight tool executions
- Persist whatever's been streamed so far
- Return to TUI prompt

Implementation: `tokio::select!` between the provider's `rx` and a `signal::ctrl_c()` future. On Ctrl-C, drop the rx → tokio cancels the spawned task → reqwest cancels the in-flight request.

### 2.5 Tool execution (default: sequential, v0.6: parallel)

**Pi's default is `parallel`** (verified: `packages/agent/src/agent.ts` line `this.toolExecution = runtimeOptions.toolExecution ?? "parallel"`), but they allow per-tool override:

```ts
if (config.toolExecution === "sequential" || hasSequentialToolCall) {
    return executeToolCallsSequential(...)
}
return executeToolCallsParallel(...)
```

`hasSequentialToolCall` is true if any tool in the batch declares `executionMode: "sequential"` (e.g. bash declares itself sequential because parallel bash invocations can interfere).

**v0.5 plan**:

| Stage | Default | `bash` tool mode | Reason |
|---|---|---|---|
| **v0.5** | `sequential` | always sequential | First stable, predictable. v0.5 ships one or two tools anyway. |
| **v0.6** | `parallel` | `sequential` | Align with Pi's semantics. Default parallel; bash auto-downgrades. |
| **v1.0** | `parallel` | `sequential` | Full Pi parity. |

Tool spec includes `execution_mode: ExecutionMode` field. v0.5 always set to `Sequential`; v0.6 marks `bash` and `edit` (file-mutation) as sequential, leaves `read`/`grep` as parallel.

## 3. Session + Config Design

### 3.1 Session file layout

v0.1 has flat files: `~/.nanopi/sessions/<uuid>.jsonl`. v0.5 keeps flat files, but adds **active session per cwd** and parent linkage for `--fork`:

```
~/.nanopi/sessions/
  by-id/
    <session-uuid-1>.jsonl         # flat files
    <session-uuid-2>.jsonl
  by-cwd/
    <encoded-cwd>                  # symlink or text file pointing to <session-uuid>
```

**Simpler alternative for v0.5**: single text file `~/.nanopi/sessions/active` mapping `cwd → session-uuid`. Tree on disk is a v1.0+ concern.

### 3.2 JSONL schema v2 (additive from v0.1)

```rust
#[derive(Serialize, Deserialize)]
#[serde(tag = "type")]
pub enum SessionEntry {
    /// First line. version=2 in v0.5.
    #[serde(rename = "session")]
    Header {
        version: u32,                 // bumped to 2
        id: String,                   // UUID v7 (see §3.3)
        parent_id: Option<String>,    // NEW: for fork support
        timestamp: String,
        cwd: String,
        model: String,
        base_url: String,
    },

    /// User prompt.
    #[serde(rename = "message")]
    Message {
        id: String,
        timestamp: String,
        role: String,                 // "user" | "assistant"
        content: String,
    },

    /// NEW: tool call + result (cleaner than inline tool messages).
    #[serde(rename = "tool_call")]
    ToolCall {
        id: String,                   // matches the call's id from provider
        timestamp: String,
        tool_name: String,
        arguments: serde_json::Value,
    },

    #[serde(rename = "tool_result")]
    ToolResult {
        tool_call_id: String,
        timestamp: String,
        content: String,
        is_error: bool,
    },

    /// NEW: model change mid-session.
    #[serde(rename = "model_change")]
    ModelChange {
        timestamp: String,
        from: String,
        to: String,
    },
}
```

**Migration from v0.1**: v0.1 wrote `{"type":"message","role":"assistant","content":"..."}` (no tool calls, no separate tool_call entry). On load, treat any v0.1 file as v=1, no migration needed — it's still valid v=2 (the new entries just won't appear).

### 3.3 UUID v7 (time-ordered ids)

v0.1 used nanosecond timestamps as ids (ugly, not unique on fast machines). v0.5 uses real UUID v7:

```rust
// Use the `uuid` crate with the `v7` feature, ~10 KB
// id layout: 48-bit unix-ms timestamp + 4-bit version + 12-bit rand + 2-bit variant + 62-bit rand
```

Trade-off: adds the `uuid` crate (~10 KB), but gives sortable, collision-resistant ids that play nicely with forks.

### 3.4 Config file

`~/.nanopi/config.toml` (v0.5):

```toml
# Default model for `--model`-less invocations
default_model = "deepseek-v4-flash"

# Default base URL (overrides flag, flag overrides env)
default_base_url = "https://api.deepseek.com/v1"

# API key source. "env" reads OPENAI_API_KEY, "file" reads from api_key_file.
api_key_source = "env"

# Optional: read key from a file (0600 perms enforced)
# api_key_file = "~/.nanopi/keys/deepseek"

# Tool execution
[tools]
default_timeout_secs = 30
bash_max_output_bytes = 30_000
bash_max_output_lines = 2000

# Trust
[trust]
default = "ask"   # ask | always | never

# Logging
[logging]
level = "info"     # trace | debug | info | warn | error
file = ""          # if set, write to this file in addition to stderr
```

Hooks live in a **separate file** (see §6) to keep config clean.

**Why TOML, not JSON**:
- Native Rust support via `toml` crate
- Comments are first-class
- Human-friendly
- Pi uses JSON for compat with Node; we don't have that legacy

### 3.5 Project-local config

`./.nanopi/config.toml` in the user's cwd overrides global. Deep-merge:
- Global: defaults
- Local: wins on key collision
- CLI flag: wins on everything

```rust
fn load_config(cwd: &Path) -> Config {
    let global = read_toml("~/.nanopi/config.toml").unwrap_or_default();
    let local = read_toml(cwd.join(".nanopi/config.toml")).ok();
    merge(global, local)
}
```

### 3.6 Skills and prompts (resource loading)

**Skills** are markdown files with YAML frontmatter, living in `~/.nanopi/skills/` or `./.nanopi/skills/`:

```markdown
---
name: debug-bash
description: 当 bash 命令失败需要诊断时调用此 skill。按 4 步走：...
---

# 调试 bash 失败的步骤

1. 重读命令，检查拼写
2. ...
```

At session start, the loader:
1. Walks all skill directories
2. Parses YAML frontmatter (name, description)
3. Injects into system prompt as:

```xml
<available_skills>
<skill>
<name>debug-bash</name>
<description>...</description>
<location>~/.nanopi/skills/debug-bash.md</location>
</skill>
</available_skills>
```

**Prompts** are reusable templates in `~/.nanopi/prompts/`:

```markdown
---
name: explain
description: 用通俗语言解释一段代码
args: code
---

请用通俗易懂的中文解释以下代码：

{code}
```

Registered as slash commands: `/explain <code>`. The user types `/explain foo.rs`, the prompt template is interpolated and sent as a user message.

**Loader mechanics**: read dir, parse frontmatter (via `serde_yaml`), build `Vec<Skill>` and `Vec<PromptTemplate>`. Inject skills into the system prompt at session start.

### 3.7 Trust model

**First run in a directory with `./.nanopi/`:**
- TUI shows: "Trust / Don't trust / Session only"
- "Trust" → write `~/.nanopi/trust/<encoded-cwd>=trusted`
- "Session only" → in-memory flag, not persisted
- "Don't trust" → write `=denied`
- On subsequent runs, check the file; if denied, skip loading all `./.nanopi/` resources

CLI overrides:
- `--approve` / `-a` — trust this run (aligned with Pi's flag)
- `--no-approve` / `-na` — distrust this run (aligned with Pi's flag)
- `--yolo` — see §4

Config override: `[trust] default = "always"` skips the prompt (loaded unconditionally).

### 3.8 File-locking for auth

If we add an auth.json (v0.6+), use `fs2` crate for `flock`-style locking:

```rust
let file = OpenOptions::new().write(true).create(true).open(path)?;
file.lock_exclusive()?;
// ... write ...
file.unlock()?;
```

Ensures concurrent `nanopi` invocations don't clobber each other's auth state. For v0.5 (env-var-only auth), not needed yet.

## 4. YOLO Mode (`--yolo`)

### 4.1 What it does

`--yolo` is the same semantics as Claude Code's `--dangerously-skip-permissions` and Codex's `--yolo`: **trust everything, no human-in-the-loop**.

**Verified**: Pi has no `--yolo`. (Full source-wide `grep -rn 'yolo'` returns 0 hits in production code. Pi uses `--approve` / `--no-approve` for project trust override, but no skip-everything flag.)

### 4.2 What `--yolo` skips

| Item | Default mode | `--yolo` mode |
|---|---|---|
| Project trust prompt (first run in cwd with `.nanopi/`) | asks | **skipped**, treats as `always` |
| `PreToolUse` hook with `decision: "block"` (or `exit 2`) | blocks | **ignored**, tool runs anyway |
| `UserPromptSubmit` hook with `decision: "block"` | blocks | **ignored** |
| `PostToolUse` hook stderr/stdout | shown | suppressed |
| Permission dialogs (e.g. write outside cwd) | asks | **skipped** |
| Tool error retry prompt | asks | **skipped** |

### 4.3 What `--yolo` does NOT skip (preserved for memory safety)

| Item | Why preserved |
|---|---|
| **Bash output truncation** (30 KB / 2000 lines, overflow to `~/.nanopi/logs/`) | 30 KB cap is an OOM guard, not a permission. Old machines need this. |
| Model self-restraint (refusals, training-time safety) | Out of our control |
| Filesystem write checks (path traversal protection) | Security, not permission |
| Network access to provider API | Always allowed (it's the whole point) |

**Justification for keeping bash truncation**: v0.5 targets 5 MB binary and 8 MB RAM. An unrestricted `cat large_file` could OOM the process. Override via `[tools] bash_max_output_bytes = 0` (0 = unlimited) at your own risk.

### 4.4 Implementation

A single `PermissionGate` struct threaded through the agent loop:

```rust
pub struct PermissionGate {
    pub yolo: bool,
    pub project_trust: TrustLevel,    // Computed at session start
    pub hooks_enabled: bool,           // from --no-hooks
}

impl PermissionGate {
    pub fn should_run_hook(&self, hook_kind: HookKind) -> bool {
        if !self.hooks_enabled { return false; }
        match hook_kind {
            HookKind::PreToolUseBlocking => !self.yolo,
            HookKind::PostToolUse => true,
            HookKind::Log => true,
            _ => true,
        }
    }
}
```

### 4.5 Warning message

When `--yolo` is set, we print to stderr (not TUI) once at startup:

```
⚠ --yolo enabled. Skipping: project trust prompts, beforeToolCall blocks,
  permission dialogs. Bash output truncation (30KB) still applies.
```

## 5. `-p` Print Mode (non-interactive)

### 5.1 What it does

`nanopi -p` runs one turn non-interactively and exits. Same semantics as Claude Code's `-p`.

```bash
# Plain text output
nanopi -p "读 /etc/hostname 告诉我内容"

# JSON output for programmatic use
nanopi -p --output json "检查代码 bug"

# Stdin for the message (pipe-friendly)
echo "explain this" | nanopi -p -

# Combine with yolo for CI
nanopi -p --yolo "auto-format src/"

# Combine with tools; full agent loop still runs
nanopi -p --yolo "read foo.rs and write a fix"
```

### 5.2 Mode differences

| Aspect | TUI mode (default) | `-p` mode |
|---|---|---|
| **Alt-screen** | enters | **does not** |
| **Stdin** | interactive (key events) | **read once** for `-` or error if TTY |
| **Stdout** | TUI rendering | assistant's final message text (or JSON) |
| **Stderr** | minor diagnostics | `[bash] cmd` / `[read] foo.rs` progress, all diagnostics |
| **Exit code** | n/a (user-driven) | 0 = success, 1 = LLM error, 2 = tool error |
| **Tool calls** | full loop | **full loop** (not just one Q&A) |
| **Session file** | written | written (same as TUI) |
| **Hooks** | enabled | enabled |
| **YOLO** | independent | independent (combinable) |

### 5.3 Output formats

`--output text` (default):
- One chunk of text to stdout: the **final** assistant message after the full tool loop settles
- Progress markers to stderr

`--output json`:
- One JSON object to stdout at the end:
  ```json
  {
    "session_id": "0190abc...",
    "messages": [
      {"role": "user", "content": "..."},
      {"role": "assistant", "content": "...", "tool_calls": [...]},
      {"role": "tool", "tool_call_id": "call_1", "content": "..."},
      {"role": "assistant", "content": "final answer"}
    ],
    "usage": {"input_tokens": 123, "output_tokens": 456},
    "finish_reason": "stop",
    "duration_ms": 5421
  }
  ```
- Progress events **stream** to stderr as JSONL (NDJSON) if `--verbose` is set

### 5.4 CLI

```rust
#[derive(Parser)]
struct Args {
    /// Non-interactive print mode (Claude Code's -p semantics).
    /// Implies no alt-screen, no event loop; exits after one turn.
    #[arg(short = 'p', long = "print")]
    print: bool,

    /// Output format for -p mode.
    #[arg(long, default_value = "text", value_parser = ["text", "json"])]
    output: OutputFormat,

    /// User message. In TUI mode: prefill the input. In -p mode: the prompt.
    /// Use `-` to read the message from stdin.
    #[arg(short = 'm', long)]
    message: Option<String>,

    // ... other flags
}
```

### 5.5 Message resolution order in `-p` mode

1. `--message` flag value (or `-` for stdin)
2. Stdin if `--message -` or no `--message` and stdin is not a TTY
3. Error: "no message provided" → exit 2

If stdin is a TTY (interactive), `-p` errors out: `-p` is for non-interactive use, no use waiting for keyboard input.

## 6. Hooks (Claude Code-style)

### 6.1 Why Claude Code's design

Pi's hooks are all in TypeScript extensions — a heavy mechanism. Claude Code's hooks are **declarative JSON + arbitrary shell commands** — lighter, more universal, and crucially: **anyone can write them** (`.sh` files).

We adopt Claude Code's model with TOML and `exit code` semantics, since it's the cleanest pattern in the agent space.

### 6.2 Configuration file

`~/.nanopi/settings.toml` (or `./.nanopi/settings.toml` for project-local), separate from `config.toml` so settings-vs-config stays clean:

```toml
# Hook definitions. Each event has a list of matcher+command pairs.
# All hooks within a matcher run in order; any one blocking stops execution.

[[hooks.pre_tool_use]]
matcher = "bash"
type = "command"
command = "~/.nanopi/hooks/check-rm-rf.sh"
timeout = 5000

[[hooks.pre_tool_use]]
matcher = "write|edit"
type = "command"
command = "~/.nanopi/hooks/auto-format.sh"
timeout = 10000

[[hooks.post_tool_use]]
matcher = "edit|write"
type = "command"
command = "prettier --write $NANOPI_FILE_PATH"
timeout = 15000

[[hooks.user_prompt_submit]]
matcher = "*"
type = "command"
command = "~/.nanopi/hooks/log-prompt.sh"
```

### 6.3 I/O Protocol

**stdin** (one JSON object, single line):

For `PreToolUse`:
```json
{
  "event": "PreToolUse",
  "tool_name": "bash",
  "tool_call_id": "call_abc123",
  "arguments": {"command": "rm -rf /tmp/foo"},
  "cwd": "/home/user/project",
  "session_id": "0190abc..."
}
```

For `PostToolUse`:
```json
{
  "event": "PostToolUse",
  "tool_name": "edit",
  "tool_call_id": "call_def456",
```

### 6.4 stdout (decision)

Two ways to communicate back; **either** works, hook picks one:

**Option A: Exit code** (simpler, bash-friendly):
- `exit 0` → allow / continue
- `exit 2` → **block**; stderr is read as the reason
- Other non-zero → runtime error (logged, not block)

**Option B: JSON on stdout** (more expressive):
```json
{
  "decision": "block",      // "allow" | "block"
  "reason": "rm -rf refused",
  "updated_input": {...},   // optional: replaces the tool arguments (PreToolUse only)
  "system_message": "..."   // optional: warning shown to user
}
```

If both exit code 2 AND JSON `decision: "block"`, JSON wins (more specific).

### 6.5 Environment variables injected into hook scripts

| Variable | Value |
|---|---|
| `NANOPI_EVENT` | `PreToolUse` / `PostToolUse` / `UserPromptSubmit` / etc. |
| `NANOPI_TOOL_NAME` | (Pre/Post only) e.g. `bash` |
| `NANOPI_TOOL_CALL_ID` | (Pre/Post only) e.g. `call_abc123` |

| `NANOPI_PROJECT_DIR` | project root (symlink-resolved) |

| `NANOPI_OUTPUT_FORMAT` | `text` \| `json` (mirror of `--output`) |

(Adapted from Claude Code's `CLAUDE_*` env var convention. We're `NANOPI_*` to keep clear ownership.)

### 6.6 Runtime behavior (Rust implementation)

```rust
// crates/nanopi-core/src/hook.rs

use std::process::Stdio;
use tokio::io::AsyncWriteExt;
use tokio::process::Command;

pub async fn run_hook(
    hook: &HookConfig,
    input: &HookInput,
    timeout_ms: u64,
) -> Result<HookOutput, HookError> {
    let input_json = serde_json::to_string(input)?;
    
    // Inject env vars
    let mut cmd = Command::new("bash");
    cmd.arg("-c").arg(&hook.command);
    cmd.env("NANOPI_EVENT", input.event_name());
    cmd.env("NANOPI_TOOL_NAME", &input.tool_name().unwrap_or_default());
    // ... other env vars
    
    cmd.stdin(Stdio::piped());
    cmd.stdout(Stdio::piped());
    cmd.stderr(Stdio::piped());
    
    let mut child = cmd.spawn()?;
    
    // Write input to stdin (line-buffered; claude code adds trailing \n)
    if let Some(mut stdin) = child.stdin.take() {
        stdin.write_all(input_json.as_bytes()).await?;
        stdin.write_all(b"\n").await?;
        stdin.shutdown().await?;
    }
    
    // Race the child against a timeout
    let timeout = tokio::time::Duration::from_millis(timeout_ms);
    match tokio::time::timeout(timeout, child.wait_with_output()).await {
        Ok(Ok(output)) => {
            // Parse exit code + stdout JSON
            parse_hook_output(output, hook.event_kind)
        }
        Ok(Err(e)) => Err(HookError::Spawn(e)),
        Err(_) => {
            // Timeout: kill the child
            child.kill().await.ok();
            // Timeout counts as "block" with reason "timeout"
            Ok(HookOutput::block("hook timed out"))
        }
    }
}
```

### 6.7 Matcher syntax

`matcher` is a regex applied to the tool name. Examples:

| Pattern | Matches |
|---|---|
| `"bash"` | only `bash` |
| `"edit\|write"` | either |
| `"*"` | all tools |
| `"^(read\|grep)$"` | exact, with anchors |
| `""` (empty) | same as `*` |

An invalid regex is a startup error.

### 6.8 YOLO + hooks interaction

In `--yolo` mode:
- `PreToolUse` hooks still **run** (so logs work)
- But their `block` decisions are **ignored** — the tool runs anyway
- `PostToolUse` hooks run normally (they can't block anyway)
- `UserPromptSubmit` block decisions ignored

This matches the principle: yolo means "no human in the loop," not "hooks can't observe."

### 6.9 Workspace trust requirement (Claude Code parity)

Per Claude Code: **all hooks require workspace trust** because they execute arbitrary commands. If a directory has `~/.nanopi/hooks/` and the user denies trust, **all hooks in that directory are skipped** with a warning, and the project-local settings.toml is also ignored.

This is a v0.5 implementation detail we should get right: trust is checked once at session start, and either:
- all hooks from that project dir are loaded
- none are, with a warning

### 6.10 Hook error policy

A hook that crashes (non-zero exit, malformed JSON, timeout) does **not** crash the agent. We log to stderr and treat as `allow` (fail open). Rationale: a broken hook shouldn't take down the user's session. Users opt into stricter behavior with `[hooks] on_error = "block"`.

### 8.1 Code organization

nanopi v0.5 needs proper module structure. v0.1 is one file because it does one thing; v0.5 has more concerns:

```

├── src/
│   ├── main.rs               # clap + dispatch
│   ├── config.rs             # config.toml loader, env vars
│   ├── session.rs            # JSONL read/write, active session per cwd
│   ├── trust.rs              # trust file management
│   ├── resources.rs          # skills + prompts loader
│   ├── settings.rs           # settings.toml (with hooks)
│   ├── agent/
│   │   ├── mod.rs            # Agent struct, prompt() entry point
│   │   ├── context.rs        # Context, ContextMessage, conversions
│   │   ├── event.rs          # AgentEvent enum
│   │   ├── loop.rs           # the actual turn loop
│   │   ├── permission.rs     # PermissionGate (yolo, hooks, trust)

│   │   ├── read.rs
│   │   ├── write.rs
│   │   ├── edit.rs
```

### 8.3 Migration path from v0.1

- v0.1's `main.rs` is replaced by a new modular `main.rs` that just dispatches to `mode::*`
- SSE parser moves from main.rs into `provider/sse.rs`, generalized to take any byte stream
- JSONL schema is a strict superset; v0.1 sessions still load (version=1 files, no tool_call entries — but no v0.1 sessions had tool calls either)

### 8.4 Risk register

| Risk | Mitigation |
|---|---|
| Tool args schema validation gets fiddly | Use `jsonschema` crate, lazy-eval (only when tool called) |
| Parallel tool execution complicates session ordering | Deferred to v0.6 (v0.5 sequential) |
| TUI rendering during streaming needs careful flushing | Use `crossterm::QueueableCommand` + flush only on chunk boundary |
| `bash` partial_json chunks fail to parse | Buffer full block, parse at content_block_stop; if parse fails, emit ToolCall with `{}` and a warning |
| `bash` tool hangs forever | Wrap in `tokio::time::timeout(30s)`; on timeout, return partial output + `is_error:true` |
| Skills grow unbounded → system prompt explodes | Cap skill description at 200 chars |
| Multiple `--extension` paths in the same skill name | Last one wins; warn at startup |
| Hook script runs forever | `tokio::time::timeout(5s)` default; on timeout, kill child, treat as block |
| Hook script hangs reading stdin | Always `stdin.shutdown()` after writing input JSON + trailing `\n` (matches Claude Code's fix for `read -r line`) |
| Hook script has shell injection risk | Documented: hooks are user-controlled, --yolo is opt-in |
| YOLO mode forgotten in a sensitive env | Print warning to stderr at startup; document loudly in README |
| `matcher` regex is invalid | Validate at startup, fail fast with line number |
| Workspace trust bypass via env var | Honor `--no-approve` to override `--approve`; both are user-explicit |
| Hook script invents `NANOPI_*` env vars (collision) | Reserve the `NANOPI_` namespace; warn if user-set env var would shadow |

### 8.5 v0.5 acceptance criteria

A v0.5 build is "done" when:

1. `./nanopi --model gpt-4o-mini --api-key ... --message "read /etc/hostname and tell me what you see"`
   - Calls `read` tool
   - Tool result returns the file contents
   - Assistant turn uses the tool result in its answer
   - JSONL has tool_call + tool_result + assistant message
2. `./nanopi --tools read,write --message "create a file /tmp/foo.txt with hello world"`
   - Uses `write` tool
   - File is actually created
3. `./nanopi -p "what is 2+2"` returns the answer to stdout, exits 0, no TUI
4. `./nanopi -p --output json "..."` returns a JSON envelope with messages + usage
5. Skill `~/.nanopi/skills/greet.md` is auto-injected into system prompt
6. `PreToolUse` hook configured to block `rm -rf` actually blocks it; the model sees the block reason
7. `--yolo` skips the project trust prompt
8. `--yolo` makes a `PreToolUse` `block` decision get **logged but not honored**
9. `Ctrl-C` during a streaming response aborts cleanly, no panic
10. Static binary, musl-linked, < 5 MB
11. No regression on v0.1's smoke test (3 baseline conversations)
