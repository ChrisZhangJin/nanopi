# v0.12 acceptance — issues raised in review, and what proves them fixed

> Every issue surfaced while walking live sessions (`dist/1.jsonl`,
> `dist/2.jsonl`, `dist/1_1.jsonl` and the two TUI screenshots), mapped
> to the test that would fail if it regressed. An entry with no test
> names the reason, so "untested" is a decision on the record rather
> than an omission.
>
> Suite at the time of writing: **575 unit + 5 + 6 + 22 integration**,
> green under `cargo test --features wasm`, and `cargo build --release`
> (no WASM runtime) still compiles.
>
> `tests/print_mode_e2e.rs` runs the real binary against a loopback
> fake `/chat/completions`, so the `-p` claims below are end-to-end
> (provider → agent loop → stdout), not renderer-only. Two things to
> know before extending it: one canned response makes the agent loop
> non-terminating, so tool rounds need the sequenced server; and a tool
> round must include a `finish_reason:"tool_calls"` chunk, because the
> loop executes tools only on `FinishReason::ToolCalls` — a fixture
> without it announces the calls and then runs nothing, which looks
> exactly like a product bug.

## 1. No way to list plugins or tools

**Reported:** the model was asked what tools it had and presented the
plugin's `greet` / `fetch_head` as built-ins, then contradicted itself
one turn later. There was no command to ask nanopi directly.

**Fixed:** `/tools` prints the live registry — the same list handed to
the provider — tagged `[builtin]` or `[plugin:<name>]` with the `.wasm`
path. `ToolSource` + `ToolRegistry::entries()` exist to make the
attribution expressible at all.

| Test | Proves |
|---|---|
| `tool::tests::entries_attributes_each_tool_to_its_source` | all 7 built-ins report `Builtin`; a plugin tool reports its plugin **and** its file |
| `tool::tests::entries_are_sorted_by_name` | name-sorted (the registry is a `HashMap`, so an unsorted listing would reshuffle per run), and a plugin tool sorts *among* the built-ins rather than being appended |
| `tool::tests::a_plugin_cannot_shadow_a_builtin_in_the_listing` | `register_external` refuses a `bash` collision, so `/tools` can never attribute `bash` to a plugin |
| `wasm::host::tests::a_plugin_tool_reports_its_origin` | `WasmTool` overrides the defaulted `Tool::source` — without the override every plugin tool would claim to ship with nanopi, which is the exact confusion `/tools` exists to remove |

**Not covered:** the rendered scrollback of `/tools` itself. It writes
through `insert_line` into a live `Term`, and the palette-sync test
(`typing_a_command_name_preselects_it`) covers reachability but not
output. Verified by eye.

## 2. Plugin tool calls printed no header line

**Reported:** `greet` and `fetch_head` produced result cards with no
`greet {…}` bar, unlike `ls` / `read`.

**Root cause:** not extension-specific. `pending_tool_call` was a
single `Option` while `tool_exec_mode` defaults to `parallel`, so every
`ToolCall` in a batch arrived before the first `ToolResult` and the last
overwrote the rest — the first card was mislabelled and later cards
rendered headerless. `ls`/`read` in one batch were mislabelled the same
way; the plugin tools only made it visible.

| Test | Proves |
|---|---|
| `mode::tui::tests::parallel_tool_calls_each_keep_their_own_bar` | two in-flight calls each retrieve their own bar, in either completion order |
| `mode::tui::tests::an_unmatched_result_falls_back_to_the_oldest_bar` | an unknown `call_id` (providers do renumber) still yields a labelled card rather than a headerless one |
| `a_parallel_tool_batch_reports_each_call_separately` (e2e) | the *pipeline* under the bug: two calls in one assistant message both execute, both report under their own name and id, and the turn reaches the model's answer |
| `one_failing_tool_does_not_abort_the_batch` (e2e) | a failing sibling does not take the batch or the turn down |

**Not covered:** that the bar renders with the right background colour
per outcome. Requires a `Term`; verified by eye against the screenshots.

## 3. `url_allowlist = ["*"]` denied everything

**Reported:** `allow_network = true` plus `url_allowlist = ["*"]` still
refused every URL.

**Two causes.** The transcript's `network access denied` came from a
pre-edit run; with the config corrected, the real fault was that `"*"`
was not a wildcard — entries were compared as hostnames, so `"*"`
matched nothing and was indistinguishable from an empty list.

**Fixed:** entries are patterns — `*` any host, `*.example.com`
subdomains only, `example.com` unchanged (host + subdomains + any
port). A star anywhere else is refused rather than widened.

| Test | Proves |
|---|---|
| `wasm::loader::tests::url_allowed_star_matches_any_host` | `*` reaches hosts the config never named |
| `wasm::loader::tests::star_does_not_widen_the_scheme_check` | `file://` / `ftp://` still refused under `*` — the wildcard widens hosts, never schemes, so it cannot become the filesystem read that `allow_fs` gates |
| `wasm::loader::tests::url_allowed_subdomain_wildcard` | `*.x` matches subdomains on a dot boundary; `evil-x` and `x.evil.com` refused |
| `wasm::loader::tests::subdomain_wildcard_excludes_the_apex` | `*.x` excludes the apex, and the bare form is how you ask for both |
| `wasm::loader::tests::a_star_in_the_middle_is_refused_not_widened` | `api.*.com` → refused, not normalised into something broader (the URL parser would otherwise drop the star) |
| `wasm::loader::tests::rules_are_independent_of_each_other` | one unparseable entry disables neither its neighbours nor the gate |
| `wasm::loader::tests::any_host_detection_matches_the_gate` | the startup warning sees `*` through the same parser the gate uses |
| `http_get_wildcard_allowlist_reaches_an_unnamed_host` (integration) | end-to-end through config → `PluginState` → host fn → real socket, using `localhost` so a same-string match cannot pass it accidentally |
| `wildcard_allowlist_still_refuses_non_http_schemes` (integration) | the scheme guard holds on the real path, not just in the matcher |

Plus the 14 pre-existing `url_allowed_*` bypass tests (userinfo,
backslash authority, SSRF, suffix, substring-in-query, IP-literal
normalisation) — all still green, which is the point: the wildcard did
not loosen them.

## 4. Grey vs white text was ambiguous

**Reported:** with a screenshot — "the last response is printed in
grey, what's the difference?"

**Root cause:** two different things shared one style. Thinking is
`DarkGray + ITALIC`; blockquotes were *also* `DarkGray + ITALIC`. So a
reply quoting its tool output (which these models do constantly) was
indistinguishable from the model muttering to itself.

**Fixed:** blockquotes get a dim `▏` gutter and legible text; thinking
keeps the dim italic.

| Test | Proves |
|---|---|
| `render::markdown::tests::blockquote_is_not_styled_like_thinking` | asserts the **absence** of the `DarkGray + ITALIC` pair, so any future restyling that drifts back into the thinking look fails by name |
| `render::markdown::tests::a_bare_gt_is_still_a_quote_line` | a bare `>` (blank quote line, emitted between quoted paragraphs) keeps the gutter instead of falling through to inline parsing |

## 5. `libunwind: bad fde: FDE is really a CIE` on the musl build

**Reported:** printed before nanopi said anything, so it read like a
crash.

**Fixed:** wasmtime registers `.eh_frame` only so a third-party
unwinder can walk guest frames; nothing here consumes it, and
`Config::wasm_backtrace` (which governs wasmtime's own backtraces)
is unaffected. `native_unwind_info(false)`, gated
`#[cfg(not(windows))]` since the Windows ABI requires the tables.

**No automated test, deliberately.** The message comes from LLVM's
libunwind, which only the musl target links; on the glibc CI/dev host
the assertion would be vacuously true and would pass even if the fix
were reverted. Verified instead by controlled A/B on a real
`x86_64-unknown-linux-musl` release build with the user's plugin:

| build | `libunwind` lines |
|---|---|
| pre-fix (stashed) | 1 |
| post-fix | 0 |

Re-verify the same way if the wasmtime major version moves.

## 6. `-p` ran reasoning into the reply

**Reported:** `./nanopi -p "greet Tom"` printed
`That's a simple greeting.Hello, Tom! — from my-plugin`.

**Root cause:** thinking deltas carry no trailing newline, so the
reply's first token continued the line. Dim SGR was the only separator,
and it survives neither a pipe nor a terminal that ignores it.

**Fixed:** one newline before the first chunk of the reply. Also
`StdoutRenderer::render_to` was extracted so the tests assert the real
bytes rather than a private flag — everything in `-p` is bytes on a
pipe, and none of it is observable by inspecting struct fields.

| Test | Proves |
|---|---|
| `render::stdout::tests::a_reply_after_thinking_starts_on_its_own_line` | the exact reported output, byte for byte, now separated |
| `render::stdout::tests::the_separator_is_emitted_once_not_per_delta` | one newline, not one per delta — the failure mode of the obvious fix, which would break the reply at every token boundary |
| `render::stdout::tests::a_reply_without_thinking_gains_nothing` | the common no-reasoning case gains no leading blank line |
| `render::stdout::tests::each_thinking_run_gets_its_own_separator` | interleaved reasoning/reply runs each separate correctly |
| `render::stdout::tests::the_separator_never_reaches_the_buffer` | display-only: `--output json` and the session record do not gain a character the model never emitted |
| `render::stdout::tests::a_tool_call_consumes_the_pending_separator` | the marker's own leading `\n` is consumed rather than doubled — no blank line between reasoning and tool card |
| `render::stdout::tests::a_reply_after_a_tool_result_has_no_extra_blank_line` | same, on the other side of the result marker |
| `reasoning_does_not_run_into_the_reply` (e2e) | the reported output, asserted on the real process's stdout with a real `reasoning_content` delta — the seam the unit tests cannot reach |
| `a_reply_without_reasoning_has_no_leading_blank_line` (e2e) | same, for the common no-reasoning case |
| `json_output_does_not_carry_the_display_separator` (e2e) | `--output json` carries the reply alone, and the reasoning does not leak into the machine-readable envelope |

Three `*_does_not_panic` tests in this module asserted nothing and wrote
to the real stdout (visible as stray `[bash ✗ …]` noise in test
output). Now assert bytes:
`a_failed_tool_result_names_the_tool_and_echoes_why`,
`a_multiline_failure_gets_a_gutter_block`,
`a_successful_tool_result_reports_size_and_timing`,
`a_tool_call_marker_names_the_tool_and_previews_the_subject`,
`text_deltas_accumulate_into_the_buffer_and_the_sink`.
