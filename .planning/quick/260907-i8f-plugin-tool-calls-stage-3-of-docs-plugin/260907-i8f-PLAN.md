**Q1. How does a nine-parameter async `run_one_tool` get called from a sync `func_wrap`?**

Two problems, two answers.

*Sync→async:* exactly `fetch_url`'s shape. `std::thread::spawn` + a private
`tokio::runtime::Builder::new_current_thread().enable_all().build()` + `block_on` +
`std::sync::mpsc` reply. A runtime that fails to build is reported in-band, never
unwrapped. One thread per plugin tool call is the accepted cost, same as a plugin fetch.

*Where the nine parameters come from:* **none of them is available at plugin-load time.**
`load_extensions` (build.rs:121) is *building* the registry when `load_all` runs — plugin
tools are pushed into it afterwards — `EventSubscribers` does not exist until build.rs:182,
and the `mpsc::Sender<AgentEvent>` is per-turn and does not exist at all outside a run.
So an `Arc<ToolRegistry>` carried in `PluginState`, which §"Implementation path is not new"
suggests, is **not implementable as written**. Say so in a code comment; do not silently
do something else.

The seam is a process-wide installed dispatch, following `notify::install_sink` and
`plugin_context`'s process-wide registry:

`src/plugin_tools.rs` (new, **not** feature-gated, for `subscriber.rs`/`plugin_context.rs`'s
stated reason — the agent loop reads it, so that path stays free of `cfg(feature = "wasm")`):

```rust
pub struct Dispatch {          // every field Clone, verified above
    registry: ToolRegistry, cwd: PathBuf, permission: PermissionGate,
    hooks: HooksConfig, subscribers: EventSubscribers,
    session_path: PathBuf, session_id: String,
}
pub fn install(d: Dispatch);                                  // idempotent, replaces
pub fn call_blocking(plugin: &str, name: &str, args_json: &str) -> String;
```

`install` is called from `Agent` construction (build.rs, after :182 where subscribers
exist) **and refreshed once per `run_turn`** at the same site stage 2 refreshes
`context.system` — that keeps `session_id` live across `/new`, `/resume`, `/fork`, which
is `claims-and-races.md` §3's session-identity row, and it is why the dispatch carries
the id rather than binding one at startup. Not installed (no Agent yet, or a `-p` path
that skipped it) → `call_blocking` returns
`error: tool calls are not available right now`. Never a panic, never a hang.

*The tx problem:* `run_one_tool` requires an `mpsc::Sender<AgentEvent>` and there is none
outside a turn. Under `Plugin` origin **every** `tx.send` in `run_one_tool` is gated off —
the rewrite notice, the block `TextDelta`, and the final `ToolResult` card — so
`call_blocking` creates a throwaway `mpsc::channel(1)` and drops the receiver. The gate is
what makes that safe; a dropped receiver alone would only make the sends fail silently,
which is a different and worse thing. A test asserts the throwaway receiver is **empty**,
so the gating is pinned rather than inferred.

`session_path` is likewise unwritten under `Plugin` origin, but the real one is passed
anyway: passing a dummy would make the invariant depend on the *caller* choosing a
harmless path instead of on the origin switch. The test asserts the real session file is
byte-unchanged across a plugin-initiated call.

**Q2. What does the plugin get back?**

Exactly §2.5: `{"content": "...", "is_error": false}` — `serde_json::to_string` of the
two fields of `ToolCallOutcome`, so a `"` in the output cannot break the frame. `images`
is dropped (no channel to a guest for it; note it in a comment).

The `error: ` convention wins over the JSON frame for *refusals*, because a refusal is not
a tool result. So the return is the JSON object when a tool actually ran, and a bare
`error: …` string when it did not:

| Situation | Returned to the guest |
|---|---|
| tool ran | `{"content":"…","is_error":false}` |
| tool ran and failed | `{"content":"tool error: …","is_error":true}` |
| blocked by a `tool_execution_start` hook | `error: blocked by hook: <reason>` |
| `allow_tools` does not name it | `error: tool "bash" is not in this plugin's allow_tools (…)` |
| target is another plugin's tool | `error: tool "x" is supplied by extension "y" — host-call-tool reaches built-in tools only` |
| target does not exist | `error: unknown tool "x"` |
| past the deadline | `error: tool call exceeded the 30s plugin deadline` |
| no dispatch installed | `error: tool calls are not available right now` |

The hook-block string is `error: blocked by hook: {reason}` **verbatim per the spec**, with
the hook's own reason last. Note the deliberate divergence: `run_one_tool` gives the MODEL
a long self-explanatory paragraph ("this is a policy refusal from the user's nanopi
configuration…") because the model needed it; the spec fixes the plugin's string, and a
plugin author reading `error: blocked by hook:` has the mechanism named already. So
`Plugin` origin returns the short form. Do this in the origin switch, not by post-hoc
string surgery on the model's paragraph.

**Q3. The `/tools` grant row pipe.**

`PluginGrants` in `src/plugin_grants.rs` (new, **not** feature-gated, same reason):
`{ plugin_name: String, path: String, grants: Vec<String> }`, where `grants` holds
already-rendered short tokens (`allow_fs`, `allow_network(github.com)`, `allow_store`,
`allow_context`, `allow_tools(find, read)`), built at load. Rendered pre-baked so the TUI
does not need `ExtensionConfig` and so the section compiles with the feature off.

Pipe: `load_all` pushes one `PluginGrants` per successfully-loaded plugin →
`PluginLoadSummary.grants` → `load_extensions` returns it → `Agent.plugin_grants:
Vec<PluginGrants>` (set at build.rs:291 and :339, i.e. both places, the stage-2 lesson) →
`app.plugin_grants_cache`, initialized empty at tui.rs:890 and refreshed in
`refresh_status` beside `subscriptions_cache` → `grants_section(&[PluginGrants]) ->
Vec<Line<'static>>` next to `subscriptions_section`, rendered right after the plugin-tool
block in `/tools`.

Honest with the feature off: without `wasm` the vec is always empty and `grants_section`
returns `Vec::new()`, so the section is **omitted entirely** rather than rendering an
empty heading — the rule `subscriptions_section` already follows. Only
*successfully-loaded* plugins get a row: a row for a plugin that failed to load would
claim a grant nothing holds.

A plugin with **no** grants still gets a row, reading `no grants`. That is the one thing
`/tools` is for here — "this plugin can do nothing" is the answer a user came to ask, and
omitting the row would make "not installed" and "installed, powerless" look identical.
