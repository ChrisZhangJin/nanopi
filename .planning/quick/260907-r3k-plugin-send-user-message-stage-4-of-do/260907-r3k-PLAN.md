<objective>
Stage 4 of `docs/plugin-capabilities.md`: `host-send-user-message(text) -> string`, gated by
`allow_send_message = true`, routed into the **existing** steer/follow-up path, always echoed
verbatim to the user, and bounded by the mandatory two-rule loop guard of §2.4 (at most one
pending message per plugin; no call during a turn that this plugin's own message started).

Purpose and danger in one sentence: this is the only import that makes a plugin **spend the
user's money**, and a plugin subscribed to `turn_start` that calls it without a guard is an
infinite loop. Everything below is about making the guard structural rather than advisory.

Output: the seventh import on `world extension`, `allow_send_message` on `ExtensionConfig`,
one new non-gated crate-root module holding the sink and the guard state, one drain site and
one turn-boundary site in `tui.rs`, an in-band refusal in `print.rs`, and one more token in
the stage-3 grant row.
</objective>

<answers_to_the_planning_questions>
These are decisions, not suggestions. Implement them.

**Q1. Where does the sink put the text, given that the TUI owns the queues?**

`steer_tx_slot` and `follow_up_slot` are **locals of the TUI turn loop**, passed by `&mut`
through `handle_action`. The plugin calls this import from a sync guest on an arbitrary
thread — during an event handler, for instance. So, exactly as stage 3 found for
`run_one_tool`'s nine parameters, neither queue is reachable from a `PluginState` built at
load time. Same answer: a process-wide installed sink, `src/plugin_send.rs`, **not**
feature-gated, for `subscriber.rs` / `plugin_context.rs` / `plugin_tools.rs`'s stated reason.

But the two halves are **not symmetric**, and the obvious fix is wrong for a reason the
codebase already documents:

- `steer_tx` is an `mpsc::Sender`. Cloneable, and it survives the agent leaving the slot
  because the channel is independent of the `Agent`. **The sink carries a clone.**
- Pushing a too-late message onto `Agent::pending_follow_ups` — the tidy-looking option —
  **cannot work during a turn.** tui.rs:1809-1817 says why in its own words: a steer that
  missed its turn is noticed "in a window where the agent has been taken out of the slot and
  cannot be written to." During a turn is precisely when a `turn_start` subscriber calls
  this. That is why the TUI already keeps `follow_up_slot` as a *second* source it cannot
  merge into the first.

So the sink owns a small **overflow queue** of its own, and the TUI drains it at tui.rs:1817
as a third `.or_else(...)` beside `follow_up_slot`. Order: `agent.pending_follow_ups` →
`follow_up_slot` → plugin overflow. The plugin goes last on purpose: a human's queued line
outranks a plugin's.

Preferred path first, though — if the steer channel is alive, send `SteerMessage::FollowUp`
on it rather than using the overflow queue, because that reaches the machinery `b90b27f`
repaired instead of a parallel one. The overflow queue is only for "no channel at all",
i.e. no turn has ever run, or the receiver is already gone.

```rust
// src/plugin_send.rs — every entry point in-band, none panics
pub struct Sink { steer_tx: Option<mpsc::Sender<SteerMessage>> }
pub fn install(s: Sink);                                  // idempotent, replaces
pub fn is_installed() -> bool;
pub fn send(plugin: &str, text: &str) -> Result<(), String>;  // guard + route
pub fn take_pending() -> Option<String>;                  // TUI drains overflow
pub fn mark_turn_origin(plugin: Option<&str>);            // called at turn start
pub fn reset_turn();                                      // beside notify::reset_turn
```

`install` is called from `Agent` construction and refreshed once per `run_turn` at the same
site stage 3 refreshes its `Dispatch` — the steer sender is per-turn, so a stale clone is
exactly the bug to avoid. Not installed → `error: sending a message is not available right
now`, the stage-3 string shape.

**Q2. The loop guard, which is the whole difficulty.**

Two rules, two pieces of state, both in `plugin_send.rs` behind one mutex.

*Rule 1 — at most one pending message per plugin.* A `HashSet<String>` of plugin names with
an unconsumed message. Inserted on a successful `send`, removed when the text is actually
handed to a turn. Second call while present → `error: a message from this plugin is already
pending`, **verbatim per §2.4**.

The subtle part is *when* it clears. Not on `send` returning, or the rule is decorative. It
clears at the moment the TUI starts or steers a turn with that text — so the sink must learn
that, which is what `mark_turn_origin` is for. A message that reached the steer channel and
was then dropped because the turn died must also clear, or the plugin is wedged for the rest
of the session; `drain_steer_to_follow_ups` is the existing "this text survived its turn"
path, so a message demoted to a follow-up stays pending until the follow-up runs.

*Rule 2 — no call during a turn this plugin's message started.* `current_turn_origin:
Option<String>`, set by `mark_turn_origin(Some(plugin))` when a turn starts from that
plugin's text, cleared by `mark_turn_origin(None)` for a human turn. Both go at tui.rs:3094,
beside `notify::reset_turn()`, because that is already the per-turn boundary and a second
boundary would drift from it. Refusal: `error: this plugin cannot send during a turn its own
message started`.

The guard is **per-plugin, not global** — plugin B may send during a turn A started. A global
flag would be easier and would break the audit-plus-rules pair of plugins the spec's own
§"The problem this fixes" is motivated by. Pin this with a test; it is the thing a careless
implementation gets wrong.

Note what rule 2 does **not** cover: A sends → turn runs → A's `turn_end` subscriber sends
again → turn runs → forever. Rule 2 is satisfied every time, because each new turn's origin
is a *new* turn. Rule 1 is satisfied too, because each message is consumed before the next.
**§2.4's two rules do not bound this, and the plan is not going to pretend they do.** Add a
third bound: a per-session cap on plugin-initiated turns, `MAX_PLUGIN_TURNS_PER_SESSION = 20`,
refused with `error: this plugin has started too many turns in this session (20)`. Announced,
per invariant 9, never silent. Record it in the spec as an addition stage 4 found, the same way
stage 3 recorded its `bash`-child limit — do not let it look like it was always there.

**Q3. Echo ordering — the spec and the code contradict each other. The code is right.**

§Required tests says "the text is echoed to the user before it is sent". tui.rs:3200-3209
says the opposite, deliberately, with the bug that forced it: the send is attempted BEFORE
the echo, because when it was the other way round the one failing case — the turn ending
between the keypress and the dispatch, dropping the receiver — printed `[steer] …` and then
discarded the text. **The user saw their message land and it was gone.**

Keep send-first. Amend the spec, do not quietly diverge from it. The property the user
actually needs is a biconditional, not an ordering:

- no send without an echo, and
- no echo without a send.

Write the tests as those two, and say in the spec why the wall-clock ordering is the wrong
assertion. This is the stage-3 pattern: the spec claim was disproved by implementing it, so
the spec changes.

**Q4. Headless mode.**

`src/mode/print.rs` does not consume `CommandAction` at all and has no steer channel — the
whole plugin-command path is TUI-only. So under `-p` the sink is never installed and
`send` returns `error: sending a message is not available right now`. That is already the
Q1 default, so the work here is only to *prove* it: a test asserting the refusal, plus a
line in the docs. Invariant 9 is the reason this cannot be a silent no-op — a plugin must
never believe it sent something it did not.

**Q5. Disclosure.**

One line per accepted message, through stage 2's `notify::disclose` on the **HOST** budget,
for stage 2's reason: a disclosure an adversary can suppress by flooding `host-notify` is not
a disclosure. Stage 3's reversion 9 is the proof this needs its own test that exhausts
`MAX_NOTIFY_PER_TURN` first — a test asserting only "one disclosure per call" passes with
the quota-consuming `notify()` too, and is therefore not testing the thing.

A refused message discloses nothing. The verbatim echo is separate from and additional to
the disclosure line; the echo is the text, the disclosure is the attribution.
