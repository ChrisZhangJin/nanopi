# 260907-d87 Plan 01: Plugin outbound surface, stage 1 Summary

Plugins can now persist keyed state across restarts (`host-store-get` /
`host-store-set`, gated on a new `allow_store`) and address the user in
attributed, rate-limited scrollback lines (`host-notify`, ungated) —
without touching the agent loop, the `EventHandler` trait, or the
`Mutex`/`try_lock` model.

## Deviations from plan

### Auto-fixed / added

**1. [Rule 2 — missing critical functionality] Newline flattening in `host-notify`**
- **Found during:** Task 3
- **Issue:** The host prefix covers the first line only. A payload of
  `"harmless\n[other] rm -rf /"` renders in scrollback as two lines, the
  second of which looks exactly like a notice from a plugin named
  `other`. The spec's required-test list names only the single-line
  forgery case, so implementing exactly the listed tests would have left
  invariant 12 (a plugin cannot impersonate another) defeated by one
  `\n`.
- **Fix:** `flatten()` collapses `\n`/`\r` to spaces; one call is one
  line, which is also what §2.3 specifies. Pinned by
  `a_newline_cannot_smuggle_a_second_attribution`.
- **Files:** `src/wasm/notify.rs`
- **Commit:** `5e1d884`

**2. [Rule 3 — blocking] `PluginEngine::build_linker` extracted**
- **Found during:** Task 2, writing the post-trap test
- **Issue:** The post-trap test needs a `PluginRebuild` with a real
  linker. A bare `Linker::new` fails at `instantiate` with
  ``import `host-log` has the wrong type`` — the linking block lived
  inline in `load` and was unreachable from anywhere else.
- **Fix:** Moved the whole linking block into `build_linker`, called by
  `load` and by the test. This also removes the standing risk of the
  load path and the recovery path drifting into differently-linked
  linkers.
- **Files:** `src/wasm/loader.rs`
- **Commit:** `400372c`

**3. [mechanical] `PluginEngine::load` call sites**
- `load` went from 6 to 9 parameters, so ~20 call sites in
  `tests/wasm_plugin_integration.rs` and `src/wasm/loader.rs` were
  updated. Purely mechanical; no assertions changed.

### Decisions the plan left to the executor

- **Stem collision refuses both claimants.** The plan asked for a
  decision and a comment. "Later one loses" makes store ownership depend
  on `[[extensions]]` ORDER, so reordering a config would silently hand
  one plugin's memory to another. Refusing both matches the command-name
  precedent (`NEITHER registers`). Stated in a comment at the call site.
- **`MAX_NOTIFY_PER_TURN = 10`**, per turn rather than per second, with
  the reasoning in the doc comment.
- **The suppression line is emitted at drain**, not at first overflow.
  The plan's phrasing ("on the FIRST overflow … and it keeps counting so
  that line's N is the real total") is not implementable as written — a
  line enqueued at first overflow can only say `1`. Emitting at drain is
  the only way N is true, and it still satisfies "once, not once per
  further call": N suppressed calls between two drains produce one line.

## Spec discrepancies found — for the developer to rule on

Per the success criteria, `docs/plugin-capabilities.md` was **not**
narrowed. Two things in the source documents turned out not to match the
code:

**1. The plan's claim that unknown `[[extensions]]` keys are refused is wrong.**
The plan's Task 2 behaviour list says "an unknown key inside
`[[extensions]]` still fails loudly, and `allow_store` is accepted".
`#[serde(deny_unknown_fields)]` is present only on `HooksSection`
(`agent/hook.rs`, the retired-key rule), **not** on `ExtensionConfig`
and not crate-wide. So `allow_stroe = true` parses fine today and grants
nothing, silently — a user believes they granted a store and did not.

I did **not** fix this: switching it on would start rejecting configs
that load today, which is a decision about every `[[extensions]]` key
rather than about `allow_store`. Instead
`a_typod_extension_grant_is_currently_ignored_not_refused` in
`src/config.rs` pins the current behaviour with the gap written into its
doc comment, so flipping it later is deliberate and visible. **Worth a
follow-up decision.**

**2. §3's `/tools` claim was overclaiming (amended, per the orchestrator's ruling).**
The section said "`/tools` must show all of them" while `/tools` carries
no per-plugin grant data at all. The row stays deferred — subscriptions
are per-plugin data the Agent already holds, whereas grants are consumed
in `load_all` and never retained, so surfacing them needs a
`load_all → Agent → App cache → render` pipe that stages 2-3 would
immediately widen. But §3 now states the gap and names the startup
`[Extensions]` notice standing in for it, rather than asserting a
behaviour the code does not have.
